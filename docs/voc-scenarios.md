# 개발팀용 VOC 조사 에이전트 — 해커톤 시나리오

[멀티모듈 구조와 데이터 흐름](architecture.md)을 기준으로 구현한다.

## 목표와 범위

- 참여 인원: 3명. 개발 기간: 2일. 주 언어와 프레임워크: Java, Spring Boot.
- 목표: 문의를 입력하면 에이전트가 소스코드·로그·데이터를 조회해 원인 후보, 근거, 해결안을 제시한다.
- 필수 문의 시나리오: 서로 다른 원인을 가진 7개. 아래 원인과 데이터는 구현을 위한 설계이며, 현재 구현된 장애가 아니다.
- 공통 기능: 상품, 주문, 재고 예약·반환과 변경 이력, 쿠폰, 모의 결제, 전체 주문 취소, 모의 환불.
- 같은 에이전트와 조사 도구를 모든 시나리오에서 사용한다.
- VOC-07의 재고 초과 판매를 주요 시연 후보로 삼는다. 추가되는 재고 처리는 기존 주문·취소 흐름에 연결한다.

## 공통 업무 규칙

앱과 에이전트가 확인할 정상 동작의 기준은 [업무 정책](business-policy.md)에 정의한다. 아래는 시나리오와 관련된 주요 규칙이다.

- 결제 성공 시 주문은 결제 완료 상태로 전이되어야 한다.
- 쿠폰의 최소 주문금액은 할인 전 상품 합계 기준이며, 기준 금액과 같은 경우도 적용 가능하다.
- 정률 쿠폰은 원 단위로 버림 처리하며, 정책에 지정된 최대 할인금액을 초과하지 않는다.
- 같은 체크아웃 요청 키로 재시도한 요청은 같은 주문을 반환해야 한다.
- 결제된 주문을 전체 취소하면 환불 상태를 추적해야 하며, 일시적인 환불 실패는 재처리 대상이어야 한다.
- 전체 취소가 완료되고 쿠폰이 아직 유효하면 해당 주문에서 사용한 쿠폰을 다시 사용할 수 있어야 한다.
- 예약 판매를 허용하지 않는 상품을 대상으로 한다. 주문 생성 시 가용 재고를 예약하며, 예약 수량은 당시 가용 재고를 초과할 수 없다.
- 전체 취소 시 해당 주문에서 예약했던 재고를 한 번만 반환한다. 재고 입고·예약·반환 이력에는 상품·주문 식별자와 수량 변화를 남긴다.

## 재현과 기대 결과

### VOC-01 — 결제 성공 후 주문 상태 불일치

- 재현: 카드와 간편결제의 두 모의 결제 수단을 준비한다. 간편결제는 승인 기록을 남기지만 주문 상태를 갱신하는 분기에서 누락되도록 구현한다.
- 근거: 결제는 승인 상태, 주문은 결제 대기 상태이며 동일 주문의 승인 이벤트 로그가 존재한다. 처리 코드에는 해당 결제 수단의 상태 전이가 빠져 있다.
- 해결안: 성공한 결제 수단을 일관되게 처리하도록 상태 전이를 수정하고, 승인 기록을 확인해 불일치 주문을 복구하는 절차를 제시한다.
- 대조 사례: 카드 결제 주문은 정상적으로 결제 완료가 된다.

### VOC-02 — 쿠폰 적용 경계값 오류

- 재현: 최소 주문금액 50,000원인 유효한 쿠폰과 합계 50,000원인 상품을 사용한다. 비교식이 기준 금액보다 큰 경우만 허용하도록 구현한다.
- 근거: 유효기간·소유자·사용 상태는 정상이고 최소 주문금액과 상품 합계가 같다. 거절 로그와 경계값을 제외하는 코드가 연결된다.
- 해결안: 업무 정책에 맞게 기준 금액을 포함하는 비교로 수정하고, 49,999원·50,000원·50,001원의 결과를 검증한다.
- 대조 사례: 49,999원은 정상적인 적용 거절이며, 50,001원은 적용된다.

### VOC-03 — 정률 할인 계산 오류

- 재현: 상품 합계 60,000원, 할인율 10%, 최대 할인금액 10,000원인 쿠폰을 사용한다. 정수 할인율을 100으로 먼저 나누어 할인금액이 0원이 되도록 구현한다.
- 근거: 쿠폰은 정상 적용으로 기록되지만 할인금액은 0원이다. 정책상 할인금액은 6,000원이며, 계산 코드에서 정수 나눗셈으로 비율이 소실된다.
- 해결안: 금액·비율 계산을 소수 연산으로 수행하고 원 단위 처리 및 최대 할인금액 정책을 명시적으로 적용한다.
- 대조 사례: 고정 금액 쿠폰은 정상 계산된다. VOC-02의 경계값을 피하는 금액으로 재현한다.

### VOC-04 — 재시도로 인한 중복 주문

- 재현: 동일 고객과 체크아웃 요청 키를 가진 주문 생성 요청을 두 번 순차 전송한다. 각각 새 주문을 생성하도록 구현한다.
- 근거: 같은 체크아웃 키에 서로 다른 주문 ID가 두 개 존재하고, 요청 로그도 두 번 기록된다. 주문 생성 경로에 해당 키를 재사용하거나 중복을 제한하는 처리가 없다.
- 해결안: 체크아웃 키의 유일성을 보장하고 재요청에는 기존 주문을 반환하도록 처리한다. 기존 중복 건은 결제 상태를 확인한 뒤 정리하는 절차를 제시한다.
- 대조 사례: 같은 고객이 서로 다른 체크아웃 키로 주문한 두 건은 정상 주문이다.

### VOC-05 — 취소 후 환불 재처리 누락

- 재현: 쿠폰을 사용하지 않은 정상 결제 주문을 취소한다. 모의 결제 시스템은 해당 환불 요청에 한 번 일시적인 오류를 반환한다. 취소 코드가 오류를 기록한 뒤 주문만 취소 완료로 남기고 환불 재처리 대상을 남기지 않도록 구현한다.
- 근거: 주문은 취소 완료지만 환불 성공 기록이 없고, 모의 결제 시스템의 일시적인 실패 로그가 존재한다. 예외 처리 경로에서 환불 상태 추적·재처리가 빠져 있다.
- 해결안: 환불 진행·실패 상태를 보존하고, 결제 시스템의 실제 환불 상태를 확인한 뒤 동일 환불 키로 재처리하는 절차를 제시한다. 재발 방지를 위해 재시도와 결과 추적을 추가한다.
- 대조 사례: 모의 결제 시스템이 정상 응답하는 주문은 환불 완료가 된다.

### VOC-06 — 취소 후 쿠폰 복원 누락

- 재현: 유효한 고정 금액 쿠폰을 적용해 정상 결제한 주문을 전체 취소한다. 모의 환불은 성공하지만 쿠폰 사용 기록을 해제하지 않도록 구현한다.
- 근거: 주문 취소와 환불은 완료됐고 쿠폰도 아직 유효하지만 해당 주문의 쿠폰 사용 상태가 남아 있다. 취소 완료 처리에 쿠폰을 복원하는 동작이 없다.
- 해결안: 주문과 연결된 쿠폰 사용 기록을 해제하는 후처리를 추가하고, 이미 취소된 해당 주문의 복원 대상 데이터를 확인하는 절차를 제시한다.
- 대조 사례: 유효기간이 끝난 쿠폰은 취소 후에도 사용 불가다. 정상 환불과 고정 금액 쿠폰을 사용해 VOC-03·05와 원인을 분리한다.

### VOC-07 — 동시 주문으로 인한 재고 초과 판매

- 재현 데이터: 특정 상품의 가용 재고 1개, 서로 다른 고객 2명, 서로 다른 체크아웃 요청 키, 각 주문 수량 1개. 쿠폰은 사용하지 않으며 두 요청 사이에 입고·취소·재고 조정은 없다.
- 취약한 처리: 재고를 조회해 수량을 검사한 뒤, 재고 조건 없이 `quantity = quantity - 1`로 차감하고 주문을 생성한다. 재현용 취약 구현에는 음수 재고를 차단하는 DB 제약이 없는 것으로 설계한다.
- 동시 실행: 두 요청이 각각 재고 1개를 읽고 검사를 통과한 후 차감하도록 테스트용 동기화 지점에서 실행 순서를 제어한다. 두 요청은 서로 다른 DB 트랜잭션과 연결을 사용한다. 동기화 대기에는 제한 시간을 두고 재현 실행이 끝나면 초기화한다.
- 기대 장애: 첫 차감 후 재고는 0개, 두 번째 차감 후 -1개가 되며 주문 2건이 커밋된다. PostgreSQL의 기본 Read Committed 환경에서 이처럼 사전 검사와 무조건 차감을 분리한 경로를 대상으로 한다.
- 로그 근거: 상품 ID, 주문 ID, 요청 ID, 체크아웃 요청 키, 요청 수량, 조회한 재고, 실제 차감 결과와 발생 시각을 기록한다. 두 요청이 같은 재고 1개를 근거로 통과했다는 사실을 확인한다.
- 데이터 근거: 초기 재고 기록과 두 주문의 예약 이력, 커밋된 주문 수량, 현재 재고를 함께 조회한다. 서로 다른 체크아웃 키도 확인해 각 요청을 식별한다.
- 코드 근거: 조회 후 검사와 실제 차감 사이에 다른 요청이 개입할 수 있고, 차감 SQL이 재고 조건을 다시 검사하지 않는 경로를 찾는다. 트랜잭션 존재 여부와 함께 선택한 격리 수준과 갱신 조건을 확인한다.
- 해당 건의 조치: 초과 주문과 실제 가용 수량을 식별하고, 운영 정책에 따른 추가 확보·주문 조정·취소 및 환불 대상을 제시한다. 재고 값은 실제 재고와 주문·예약 이력을 대조해 보정하도록 안내한다.
- 재발 방지: 재고 조건을 포함한 원자적 차감을 적용하고 영향받은 행 수로 성공 여부를 판단한다. 주문 생성·재고 예약·예약 이력 저장은 같은 DB 트랜잭션으로 묶는다.

수정안 예시이며, 현재 실행하거나 구현한 SQL은 아니다. `:quantity`는 양의 정수로 검증한다.

```sql
UPDATE product_stock
SET quantity = quantity - :quantity
WHERE product_id = :productId
  AND quantity >= :quantity;
```

영향받은 행이 1개일 때 주문을 생성하고, 0개이면 재고를 확보하지 못한 것으로 처리한다. 주문 저장이 실패하면 같은 트랜잭션의 재고 차감도 롤백되어야 한다. PostgreSQL Read Committed에서 경쟁하는 UPDATE는 선행 갱신을 기다린 뒤 갱신된 행에 WHERE 조건을 다시 평가한다. 이 동작을 이용한 수정안이다. [PostgreSQL 트랜잭션 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html)

- 수정 검증: 조회 이후의 취약 경로용 동기화 지점은 해제하고, 별도 시작 신호로 두 요청을 동시에 실행한다. 재고 1개·주문 2건 시 성공 1건/재고 부족 1건/잔여 재고 0개여야 한다. 재고 2개·주문 2건 시 둘 다 성공해야 하며, 순차 실행에서도 수량 보존을 확인한다.
- 확장 검증: 재고 10개에 서로 다른 요청 20건을 보내 주문 성공 수량이 10개이고 잔여 재고가 0개인지 확인한다. 다른 오류는 재고 부족과 구분해 기록한다.
- 진단 시 주의할 표현: 재고를 읽은 뒤 계산한 절대값을 저장하는 구현에서는 두 요청이 모두 0을 저장해 DB 재고가 음수가 되지 않아도 초과 판매가 발생할 수 있다. 초과 판매 여부는 확보한 재고·예약 수량·성공 주문을 함께 대조해 판단한다.
- 독립 재현: 다른 시나리오는 충분한 재고로 순차 실행한다. VOC-07은 지정 상품의 재고·이력·주문을 초기화한 뒤 독립 실행해 다른 장애의 영향을 분리한다.

## 공통 조사 도구와 결과

- `findOrders`: 고객·시간 범위·체크아웃 요청 키로 주문 후보를 찾는다.
- `getOrderContext`: 특정 주문의 상품·수량·금액·주문 상태·결제·환불·쿠폰 사용 내역을 조회한다.
- `getCouponContext`: 고객의 쿠폰 소유·사용 상태와 할인 정책을 조회한다. 주문 생성 이전에 실패한 쿠폰 문의도 조사할 수 있어야 한다.
- `getInventoryContext`: 상품과 시간 범위로 초기·현재 재고, 입고·예약·반환 이력, 관련 주문과 요청 식별자를 조회한다.
- `searchLogs`: 상품 ID·주문 ID·요청 ID·체크아웃 요청 키·시간 범위로 로그를 검색한다.
- `searchCode`와 `readCode`: 실제 실행한 버전의 앱 소스코드를 검색하고 파일 경로·줄 번호와 함께 읽는다.
- `readBusinessPolicy`: 공통 업무 규칙을 조회한다.

분석 결과에는 문의 요약, 확인된 사실, 원인 후보, 근거 참조, 해당 건의 조치, 재발 방지 수정안, 부족한 정보를 포함한다. 각 근거는 실제 도구 반환값의 로그·레코드·파일 위치를 가리켜야 한다.

이 문서의 설계 원인과 평가 정답은 평가 자료로 관리한다. 에이전트의 소스 검색 범위는 앱 소스코드로 한정하고, 업무 정책은 별도로 제공한다. 시연에는 자연어 문의와 조사에 필요한 식별자를 전달한다.

## 3명 작업 분담 제안

| 담당 | 공통 작업 | 담당 시나리오 |
| --- | --- | --- |
| A | 상품·주문·재고·결제·취소 흐름, 추적 식별자와 로그 | VOC-01, VOC-04, VOC-05·06 취소 처리, VOC-07의 재고 처리 |
| B | Spring AI 조사 흐름·공통 도구 연결, 쿠폰 로직 | VOC-02, VOC-03 |
| C | 문의·분석 프론트와 Vercel 연결, API·이력 연결, 평가 실행 | VOC-05·06 재현·검증, VOC-07의 동시 요청 재현 |

첫 한 시간에 공통 모델·도구 입출력·업무 정책을 맞춘다. 각 담당자는 자신의 시나리오 재현 데이터와 로그를 함께 준비하고, 타 담당자가 문의를 바꿔 검증한다. VOC-07은 A가 재고 처리를, C가 재현 실행을, B가 재고 조사 도구와 근거 연결을 맡는다. 문의·답변 화면과 배포 범위는 [프론트 설계](frontend-deployment.md)를 따른다.

## 이틀 일정과 완료 기준

- 첫날 오전: 공통 모델과 최소 주문 흐름, 모델 연결과 도구 호출을 확인한다.
- 첫날 오후: 대표 문의 1개를 실제 근거로 끝까지 분석하고, 7개 재현 데이터와 장애 조건을 준비한다. VOC-07의 동시 실행과 증거 기록도 이때 확인한다.
- 둘째 날 오전: 7개 모두 에이전트로 조사해 근거 참조와 원인 판단을 확인하고 실패한 경로를 보완한다.
- 둘째 날 오후: 정상·정보 부족 사례를 포함해 검증하고, 조사 시간과 검토 시간을 측정하며 데모를 안정화한다.

완료 기준:

1. 7개 문의가 각각 독립적으로 재현되고, 초기화 후 다시 실행할 수 있다.
2. 각 문의에서 코드·로그·데이터를 연결한 원인 후보와 실행 가능한 해결안을 제시한다.
3. 정상적인 거절·정상 주문을 장애로 단정하지 않고, 증거가 부족하면 필요한 추가 정보를 제시한다.
4. 주문번호와 문의 표현이 바뀌어도 조회한 근거에 맞게 판단한다.
5. 실제 관찰한 성공 여부·오진 여부·소요 시간을 기록한다. 에이전트 결과에 대한 사람의 검토 시간도 포함한다.
