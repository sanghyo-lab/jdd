# JDD 7개 VOC 시연 영상 제작 프롬프트

아래 본문을 영상 제작을 담당할 Codex 세션의 작업 지시로 사용한다. 함께 읽을 [시나리오·정답 검수·내레이션 초안](../planning/jdd-demo-video-storyboard.md)이 있다.

이 문서의 작성 범위는 **제작 준비와 프롬프트**다. 영상·PPT·음성이 이미 만들어졌거나 일곱 실제 AI 조사가 모두 통과했다는 뜻이 아니다. 이후 이 프롬프트를 실행하는 세션이 아래 제작과 검수를 수행한다.

## 실행할 작업 지시

당신은 JDD 시연 영상의 제작 총괄이다. 실제 프로젝트 화면을 Playwright로 녹화하고, 표지 1장과 시나리오 소개 7장, 한국어 성인 여성의 부드러운 합성 내레이션, 한국어 자막을 편집해 완성하라. 사용자가 쓴 “playweight”는 Playwright로 해석한다.

아래 순서를 지켜라. **먼저 화면을 녹화하고 화면만 1.5배속으로 편집한다. 그 결과를 기준으로 내레이션을 정상 1.0배속으로 제작·배치한다.** 화면과 음성을 함께 배속하지 않는다. 정답지는 제작자만 검수에 사용하고 서비스 AI에는 고객 문의와 실제 식별자만 보낸다.

### 1. 전문가 역할과 협업

- 총괄: 최신 코드·실행 빌드·정답지·실제 보고서를 대조하고 일정표와 산출물을 통합한다.
- PPT 아트디렉터: Presentations 스킬을 읽고 편집 가능한 8장 PPTX와 1080p PNG를 만든다. 본편 녹화와 독립적으로 진행한다.
- Playwright 촬영 담당: Playwright 스킬을 읽고 실제 UI를 탐색·녹화한다. 세션·DB·재현 데이터·원본 영상·이벤트 시각을 관리한다.
- 영상·음성 감독: 원본 녹화가 생긴 뒤 화면 1.5배속, 정상 속도 한국어 여성 음성, 자막과 프레임·샘플 타임라인을 편집한다.

가용 동시 실행 슬롯 안에서 독립 작업만 위임한다. 파일 소유자를 정하고 같은 브라우저 세션이나 타임라인을 동시에 편집하지 않는다. 촬영이 끝난 담당자의 슬롯은 결과 검수에 재사용한다. 모든 전문가는 같은 실제 데이터·보고서·타임라인 버전을 사용한다.

### 2. 먼저 확인할 프로젝트 자료

1. 저장소의 AGENTS.md와 역할·협업 지침, 현재 `git status`, 세 담당자·리더 상태, 논의 목록.
2. [시나리오](../voc-scenarios.md), [정상 업무 정책](../business-policy.md), `fixtures/commerce/VOC-01`~`VOC-07` 각각의 `README.md`, `expected.md`, seed/reset.
3. [화면 설명](../../web/README.md), [runner](../../scenario-runner/README.md), [AI 실행 계약](../llm-runtime.md), [비용 정책](../planning/demo-llm-policy.md), 실제 구현 코드와 최근 검증 산출물.
4. 이 프롬프트에 연결된 스토리보드. 기대값과 실제 관측이 다르면 실제 실패를 보존하고 해당 성공 대본을 사용하지 않는다.

2026-09-22 준비 조사 기준 커밋은 `86d6f6a`다. 그 시점의 실제 runner는 VOC-01 통과, VOC-02의 원인 항목 DATA 직접 인용 누락으로 실패, 후속 case는 PENDING이었다. v6 보완의 효과는 이 준비 작업에서 재검증하지 않았다. 촬영 시작 시 최신 상태를 다시 확인하고 이 과거 관측을 현재 결과로 단정하지 않는다.

### 3. 사전 준비와 실제 결과의 진위

- 진행 중인 다른 세션의 앱·DB·브라우저·미커밋 변경을 보존한다. 별도 clone/포트/Compose 프로젝트를 쓰거나 기존 촬영 환경의 소유 범위를 확인한다. 녹화 중에는 빌드·provider 변경·일반 publish를 하지 않는다.
- 로컬 영상 시연은 기존 계약의 `local/codex_oauth`를 사용한다. 마지막 사용자 지정 모델은 `gpt-5.6-luna`지만 실제 접근과 최신 선택을 확인한다. 앞선 배포 API 1회 연결 성공을 7개 조사 품질 성공으로 재사용하지 않는다.
- 배포용 프로모션 키·API 장부를 음성 합성이나 촬영 재시도에 자동 전용하지 않는다. 별도로 제공되지 않은 외부 TTS 인증·비용·라이선스를 있다고 가정하지 않는다. 인증·키·로그인 화면은 녹화하지 않는다.
- `/shop`, `/tickets`, `/tickets/{실제 ID}`와 분석·근거 패널이 실제 backend에 연결되는지 확인한다. 현재 DOM에서 선택자를 관측한다. 테스트 대역, `route.fulfill`, 응답 치환, 보고서 DOM 주입, 성공 상태 편집으로 시연을 만들지 않는다.
- 재현은 합성 전용 prefix로 실제 Commerce HTTP/DB에서 수행한다. 초기화는 해당 prefix만 대상으로 하고 과거 조사 근거·로그·비용 장부를 지우지 않는다. 결제·환불은 모의 결제 제공자임을 본편에 짧게 표시한다.
- VOC-02는 같은 쿠폰으로 50,001원 대조 주문을 먼저 성공시키면 USED가 되어 문의 조건이 바뀐다. runner 준비 경로처럼 50,000원 실패만 보존하고 대조는 다른 prefix/쿠폰으로 분리한다.
- VOC-05의 환불 실패 제어, VOC-07의 두 독립 트랜잭션 장벽은 내부 준비 도구로 수행한다. 현재 `/shop`에 이 제어 UI는 없다. Agent·web·ngrok에 내부 제어를 노출하지 않는다. 사전에 실제 생성한 상태는 “사전 재현 데이터”로 표시하고 UI에서 방금 재현한 것처럼 편집하지 않는다.
- 실제 조사 결과가 이미 있고 동일 사건·build·정책·근거의 품질 검수를 통과하면 재조회해 촬영한다. 화면에 “실제 조사 결과 재생”을 표시한다. 과거 결과를 새 요청의 결과로 연결하지 않는다. 필요한 새 조사는 실제 입력으로 한 번 접수하고 같은 요청 재전송과 새 조사를 구분한다.
- `expected.md`·이 프롬프트·스토리보드·정답 표·평가용 snapshot을 서비스 AI 메시지, 도구 반환값, 검색 경로에 넣지 않는다. 준비 manifest 전체를 context로 넘기지 않는다. 고객 문의에는 결함 이름·원인 코드·해결 SQL을 넣지 않는다.
- 각 case의 실제 보고서·모델 관측·DATA/LOG/CODE/POLICY 원문을 독립 검수한다. COMPLETED만으로 합격하지 않는다. 원인·조치·예방 각각의 직접 인용과 내용 일치를 확인한다. 실패 case는 기존 실패를 보존하고 담당 수정·재검증이 끝날 때까지 최종 성공 영상에 넣지 않는다. 준비된 다른 장표·음성 초안·촬영 편집은 계속할 수 있다.

### 4. 영상과 장표 규격

| 항목 | 제작 기준 |
| --- | --- |
| 최종 영상 | 1920×1080, 16:9, 30fps 고정, H.264/yuv420p MP4, AAC 48kHz, faststart |
| 작업 원본 | 화면 영상과 무압축 PCM WAV를 분리 보존. 편집용 오디오는 48kHz로 통일 |
| 화면 녹화 | 실제 지원 시 1920×1080·60fps. 해상도·실제 PTS·프레임 수를 녹화 파일에서 검증 |
| 화면 속도 | 유지한 본편 원본 전체를 1.5배속. 필요한 읽기 정지는 원본 녹화에 포함 |
| 내레이션 | 한국어, 차분하고 부드러운 성인 여성 음색, 정상 1.0배속, 전 case 동일 목소리 |
| 장표 | 표지 1장 + case 7장 = 총 8장. 표지는 4초/120프레임, case마다 2초/60프레임 |
| 장표 음향 | 전부 무음. 앞뒤 발화·자막·음악·잔향이 침범하지 않음 |
| 본편 자막 | 발화와 같은 내용의 한국어 자막. 번인 버전과 UTF-8 SRT·ASS를 함께 제공 |
| 길이 | 본편 case당 약 40~50초, 전체 약 5~6분을 초안 목표로 삼되 실제 발화 측정 뒤 확정 |

표지 문구는 “JDD 프로젝트 / 고객 문의의 원인을 조사하는 AI 에이전트 / 시연 영상”. 7개 소개 장표의 정확한 문구는 스토리보드를 따른다. 추가 결론 장표나 반복 로고 애니메이션은 만들지 않는다.

현재 웹의 녹색 계열과 맞춰 짙은 녹색 `#153D33` 바탕, 제목 `#F5F7F3`, 보조 `#B9D8CA`를 사용한다. 큰 제목 한 줄·설명 한 줄·case 번호만 놓는 단순한 타이포그래피다. 좌우 160px·상하 108px 이상 여백, 1080p 기준 제목 약 96px·설명 48px·case 번호 40px를 시작점으로 실제 렌더를 검수한다. 표지 제목은 약 120px다. Pretendard 또는 Noto Sans CJK KR의 설치와 한글 렌더를 확인하고 한 글꼴로 통일한다.

PPT는 Presentations 스킬의 `@oai/artifact-tool` JavaScript ES modules로 만들고 원본 텍스트를 편집 가능하게 유지한다. 스킬이 요구하는 템플릿 선택·구현·최종 렌더 검수 절차를 따른다. 장식 이미지나 프로그램으로 그린 장식 도형을 추가하지 않는다. LibreOffice가 필요하면 `load_workspace_dependencies`로 확인한 번들 절대 경로만 쓰고 사용자 데스크톱 설치본은 실행하지 않는다. 현재 번들 경로는 미확인이다.

### 5. Playwright 촬영

촬영 전에 `npx`와 Playwright 스킬의 wrapper를 확인한다. 2026-09-22 이 PC에서 확인한 캐시 `@playwright/cli 0.1.21`에는 `video-start`, `video-stop`이 있고 `recording-start`는 동작 코드 기록이다. 실제 실행 버전의 `--help`로 다시 확인한다. 녹화 시작 전에 viewport를 고정하고 로그인·쿠키 배너·로딩·글꼴 준비를 끝낸다.

```bash
# 실행 예시. base URL/세션/파일은 실제 확인값으로 지정한다.
export PWCLI="$HOME/.codex/skills/playwright/scripts/playwright_cli.sh"
"$PWCLI" --help
"$PWCLI" video-start --help
```

확인된 녹화 문법은 `video-start <원본 파일> --size=1920x1080 --fps=60`과 `video-stop`이다. 전용 세션 옵션은 현재 도움말에서 확인해 같은 세션을 지정한다. `--cursor`를 사용하면 CLI가 액션마다 추가하는 약 800ms 페이싱도 원본 시간에 포함한다. [공식 CLI 명령](https://github.com/microsoft/playwright-cli#commands)을 참고하되 실제 설치 버전의 동작을 우선 검증한다.

관측한 DOM의 최신 snapshot에 있는 ref나 실제 확인한 role/label을 사용한다. 페이지 이동·모달·분석 결과 변화 뒤에는 snapshot을 갱신한다. 없는 버튼·고정 예제 ref를 클릭하는 스크립트를 만들지 않는다. CLI 중심으로 진행하고 영상 제작을 위해 불필요한 `@playwright/test` 회귀 체계를 새로 만들지 않는다.

1. 화면별로 `문의/증상 → 실제 결과 → DATA → LOG·CODE·POLICY → 사람 조치`의 의미 구간을 정한다. 모든 키 입력을 보여줄 필요는 없다. 숫자와 핵심 근거가 최종 화면에서 읽히도록 브라우저 확대·crop을 먼저 검수한다.
2. 짧은 합성 샘플을 녹화해 커서·글자·스크롤·영상 크기·fps를 검증한 뒤 7개를 각각 독립 원본으로 촬영한다. 원본 시스템 소리는 사용하지 않는다.
3. 커서는 다음 대상까지 완만하게 이동하고 클릭 직전 잠시 멈춘다. 긴 스크롤을 한 번에 하지 않는다. 최종 1.5배속 화면을 보고 피로감이 있으면 원본 동작을 더 천천히 다시 찍는다.
4. 각 구간의 실제 원본 in/out PTS, 클릭 대상, report/근거 표시 시각을 이벤트 목록에 남긴다. CPU 부하로 프레임이 누락되면 파일의 실제 PTS를 기준으로 편집한다. 60fps 요청만으로 60fps 촬영 성공을 주장하지 않는다.
5. 모델 대기가 긴 경우 원본은 보존하고 본편의 무동작 대기만 잘라 “조사 대기 구간 생략”을 표시한다. 실제 서비스 응답 시간이 편집 길이와 같다고 설명하지 않는다. 성공·실패 상태를 바꾸거나 다른 사건 결과를 이어 붙이지 않는다.
6. 재촬영은 가능한 한 같은 저장 결과를 재조회한다. 보기 좋은 화면을 얻으려고 자동 새 분석·유료 호출을 반복하지 않는다.

브라우저 원본·snapshot은 저장소 관례의 `output/playwright/jdd-demo/<run-id>/` 아래에 둔다. 다른 세션 브라우저를 닫지 않는다. `video-stop`과 해당 녹화 context의 정상 종료 후 파일이 완전히 기록됐는지 확인한다.

### 6. 음성 1.0배속과 화면 1.5배속의 동기화

이 작업의 기준은 **녹화한 화면을 먼저 1.5배속으로 만든 후, 그 화면의 의미 구간에 맞춰 정상 속도 음성을 만드는 것**이다. 글자 수로 음성 길이를 확정하지 않는다. “한 case 45초”도 합성 전에는 목표값이다.

1. 각 원본에서 의미 구간 j의 유지 구간 길이를 `R_j`초로 측정한다. 동작 영상 길이는 `D_j = R_j / 1.5`. source trim과 `setpts=(PTS-STARTPTS)/1.5`, 최종 fps 변환은 영상에만 적용한다. 원본 CFR 60fps를 확인하고 유지 구간의 프레임 수를 3의 배수로 정하면 source 3프레임이 최종 30fps 1프레임에 정확히 대응한다. 이 조건이 아니면 처리 후 실제 프레임 수로 경계를 다시 계산한다.
2. 먼저 무음의 1.5배속 가편집을 만든다. 문의, 실제 숫자, 로그, 코드, 조치가 보이기 시작하는 의미 cue를 기록한다. 해당 cue를 보면서 스토리보드 초안을 실제 관측에 맞게 다듬는다.
3. 같은 목소리·기본 정상 속도로 문장 또는 의미 구간별 WAV를 합성한다. 발음은 “제이디디”, “브이오씨”, “오만 원”, “십 퍼센트”처럼 자연스럽게 읽는다. 원인·숫자·조치 단정은 검수된 실제 화면과 일치해야 한다.
4. 이 PC에는 `say`의 ko_KR `Yuna` 등 후보가 있으나 음질·여성 음색의 부드러움은 아직 청음하지 않았다. 제작 시 후보의 5~10초 샘플을 정상 속도로 청음하고 적합한 동일 목소리를 선택한다. 특정 인물의 목소리를 모방하거나 복제하지 않는다. 적합한 로컬 음성이 없으면 음성 선택을 미확정으로 남기고 외부 TTS의 별도 사용 범위를 확인한다.
5. 음성은 무압축 WAV의 실제 유효 발화·자연스러운 문장 끝을 측정한다. `atempo`, 배속, 피치 변경, 문장 중간 절단으로 길이를 맞추지 않는다. 무음 앞뒤만 필요한 만큼 정리하며 문장 내부의 자연스러운 쉼은 보존한다.
6. 음성이 화면보다 길면 필요한 근거 화면을 읽는 시간을 원본 촬영에 더 확보해 해당 구간을 재녹화하고 다시 1.5배속 처리한다. 불필요한 설명은 사실을 잃지 않게 줄여 동일 1.0배속으로 다시 합성할 수 있다. 음성이 짧으면 불필요한 원본 대기를 덜어내거나 그 화면의 핵심 설명을 보완한다. 편집에서 정지 프레임을 뒤에 붙여 전체 1.5배속 조건을 바꾸지 않는다. 발화가 끝난 뒤 긴 무음 꼬리를 붙여 완료로 처리하지 않는다.
7. 화면상 항목이 나타나기 전에 해당 수치·원인·조치를 읽지 않는다. 명칭과 핵심 수치가 발화되는 동안 해당 근거가 보이도록 cue별로 배치한다. case 전체 길이만 일치시키고 중간의 말/화면 불일치를 방치하지 않는다.
8. 영상·장표·case 경계는 정수 프레임, 실제 발화 위치는 정수 샘플로 관리한다. 최종 30fps·48kHz PCM에서 1프레임은 1,600샘플이다. 영상 경계의 오디오 위치는 프레임×1,600으로 계산하되 발화 시작까지 프레임 경계로 강제하지 않는다. 필요한 선행 무음과 문장 사이의 쉼을 샘플 단위로 조정한다. case별 `N_i`프레임·오디오 `N_i×1,600`샘플로 완성한 뒤 이어 붙여 누적 오차를 막는다.
9. 각 case의 마지막 문장은 마지막 의미 화면에서 끝난다. 자연스러운 발화 끝을 case 종료 샘플에 배치하는 것이 목표이며 최종 1프레임(약 33ms)은 청음·영상 검수의 허용오차다. 발음의 끝을 잘라 맞추지 않는다. 마지막 부분의 불일치는 원본에서 근거를 읽는 시간·대본·재합성으로 해결한다. 장표로 이전 발화가 넘어가면 실패다.
10. 장표는 본편 1.5배속 처리 이후에 최종 타임라인에 넣는다. 전체 합본에 `setpts/1.5`를 적용해 2초 장표까지 줄이지 않는다. 표지/장표에는 정확한 길이의 무음 PCM을 놓고 hard cut한다.
11. 길이 일치를 숨기는 `-shortest`로 음성이나 화면을 잘라내지 않는다. 가능하면 PCM 타임라인에서 모든 구간을 합친 뒤 AAC를 마지막 한 번만 인코딩한다. AAC priming/padding·container time base를 고려해 최종 디코딩한 시작/끝과 case 경계도 검증한다.

### 7. 자막과 최종 검수

자막은 최종 WAV의 발화 시각에 맞춰 작성한다. 정렬 도구가 있으면 한국어 인식 결과를 대본과 수동 대조하고, 없으면 파형·청음을 보며 문장 단위로 맞춘다. 원본 녹화 시각이나 대략적인 글자 수를 그대로 SRT 시각으로 쓰지 않는다.

- 두 줄 이내, 한 줄 약 20~26자부터 가독성을 검수하고 긴 문장은 의미 단위로 나눈다. 숫자·부정·조건을 생략하지 않는다. 1080p 기준 44~48px 한글과 충분한 외곽선/반투명 배경을 사용한다.
- 좌우 120px·하단 80px 이상 안전 영역을 두고 조치·버튼·핵심 근거를 가리지 않는다. 필요하면 촬영 단계에서 중요 내용을 위로 스크롤하거나 영상의 별도 자막 여백으로 재배치한다. UI 내용을 고쳐 공간을 만들지 않는다.
- 표지와 case 소개 2초에는 내레이션 자막을 모두 종료한다. 설명 장표의 텍스트가 자막 역할을 대신한다.
- `ffprobe`로 해상도·고정 fps·프레임 수·샘플레이트·실제 duration을 확인한다. 최종 프레임 수는 `120 + 7×60 + ΣN_i`, PCM 샘플 수는 그 값×1,600과 일치해야 한다. 오디오 불일치, 검은 빈 프레임, 마지막 발화 잘림을 디코딩한 결과에서도 검사한다.
- 전편을 실제 정상 재생 속도로 청음·시청한다. 7개 시작/중간/마지막과 장표 전후를 검사하고 의미 cue 차이 100ms 초과, 종료 차이 1프레임 초과는 수정한다. 기계적 길이 검사는 의미 검수를 대신하지 않는다.
- 목소리 크기는 전체에서 일관되게, clipping 없이 조절한다. 기본은 음악·효과음 없음이다. 정상 볼륨으로 들리는지 청음하고 음량 정규화로 발화 길이를 변경하지 않는다.
- 음성이 합성임을 다운로드 설명에 명시한다. 영상 자체의 표지 설명란에도 작게 “AI 합성 음성”을 넣을 수 있으나 별도 장표를 추가하지 않는다.

### 8. 필요한 편집 도구와 산출물

2026-09-22 준비 시점에는 PATH의 범용 `ffmpeg`·`ffprobe`가 없었다. Playwright 전용 ffmpeg는 녹화용 제한 빌드여서 최종 합성 도구로 간주하지 않는다. 제작 전에 H.264/AAC, fps/setpts, concat, subtitle/ASS/libass, 48k PCM을 처리하는 편집 도구와 한글 글꼴을 준비하고 짧은 샘플로 확인한다. 확인되지 않은 명령 옵션·인코더·TTS 기능은 만들어내지 않는다.

편집의 시간 변환·자막·오디오 필터는 [FFmpeg 필터 공식 문서](https://ffmpeg.org/ffmpeg-filters.html), 파일/프레임 계수는 [FFprobe 공식 문서](https://ffmpeg.org/ffprobe.html)를 참고하고 설치본의 실제 지원 여부를 확인한다. 로컬 Codex OAuth가 음성 합성까지 제공한다고 가정하지 않는다.

완성물은 `output/jdd-demo/<run-id>/`에 만들고 기존 파일을 덮어쓰지 않는다. 실제 영상·음성·실행 관측은 Git에 넣지 않는다. 추적이 필요하면 소스·비밀 없는 설정 예제·대본·상태만 명시적으로 공유한다.

- `jdd-demo-ko.mp4`: 7개 case, 정상 음성, 번인 자막, 무음 표지/소개 장표.
- `jdd-demo-clean.mp4`: 같은 내용·음성의 자막 없는 버전.
- `jdd-demo-slides.pptx`와 `slides/00-cover.png`~`07-voc-07.png`: 총 8장, 편집 가능한 원본과 렌더.
- `jdd-demo-ko.srt`, `jdd-demo-ko.ass`, `narration/`: 최종 자막·확정 대본·case/문장별 정상 속도 WAV.
- `timeline.json`: case/구간별 source path·PTS in/out·1.5배속·원본 내 읽기 정지·최종 start/endFrame·audio start/endSample·자막 cue. 구간은 `[start, end)`로 관리한다. 측정 전 값은 null로 두고 렌더 전에 모두 확정한다.
- `case-map.json`: 실제 case→prefix/buildId/ticketId/analysisRequestId/investigationId/model/provider/근거/검수 결과. 정답·raw 근거와 서비스 입력은 별도 보관한다. 없는 ID·usage·모델 결과를 만들지 않는다.
- `qa-report.md`: 7개 진위/품질, slide frame count, audio/video/자막 cue, 실제 재생 검수, 실패·제약·재현 명령·버전·파일 해시.
- `README.md`: 재편집/재렌더 방법, 원본 위치, AI 합성 음성 표기, 녹화/편집으로 생긴 대기 생략과 실제 조사 시각의 구분.

일곱 케이스·8장 장표·실제 결과 진위·음성/자막 동기화가 모두 확인된 뒤 영상 제작 완료를 보고한다. 영상 완성이 프로젝트의 role DONE·리더 승인·team-check를 대신하지 않는다. 실제 촬영/합성에 필요한 입력만 남으면 구체적인 누락과 완성된 산출물을 구분해 보고한다.
