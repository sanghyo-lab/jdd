# 이상효 — 커머스 구현·개발리더 상세 goal 프롬프트

이 문서는 실행할 goal의 전체 지시문이다. 문서 준비 자체는 goal을 시작하지 않는다.
이상효의 PC에서 저장소를 연 뒤 다음과 같이 시작한다.

```text
/goal AGENTS.md와 docs/prompts/implement-commerce-and-lead.md 전체를 읽고 이상효의 커머스 구현·개발리더 목표를 수행해. GitHub main을 계속 확인·반영·공유하며 구현→실행→검증→수정을 이어가. 세 담당자의 유효한 DONE, 개발리더의 독립 검토와 APPROVED가 GitHub에 공유되고 최신 main에서 team-check가 성공하며 필수 산출물과 검증이 모두 갖춰질 때만 완료해. 데모용 LLM 키의 사용 범위와 예산은 docs/planning/demo-llm-policy.md를 따라.
```

이미 이 목표가 진행 중이라면 새 goal을 만들지 말고 현재 목표에 이 문서의 기준을 반영한다.

## 1. 목표와 사용자의 문제

운영 문의를 받은 개발팀이 소스코드·로그·DB를 직접 찾고 대조하는 시간을 줄이는 내부 도구 JDD를 완성한다.
합성 데이터로 시연할 하나의 일관된 제품에 집중한다. 정상 커머스 사용에서 문의 접수, AI 조사,
근거 확인, 원인·해결안 리포트까지 실제 애플리케이션을 연결한다.

나는 이상효다. 커머스 담당과 개발리더를 함께 수행한다. 다른 담당자의 완료 선언만으로 프로젝트를 완료하지 않는다.
내 PC에서 전체 코드와 실제 동작을 독립적으로 검사하고 필요한 수정·보완까지 책임진다.
계획·설계·기동 골격·초안에서 끝내지 말고 아래 완료 기준을 충족할 때까지 작업한다.

## 2. 팀, 저장소와 실행 구조

- 저장소: https://github.com/sanghyo-lab/jdd.git. 세 사람 모두 독립 clone의 main에서 작업한다.
- 이상효: commerce-app/core/infra, 합성 데이터·재현·조사 근거, 전체 개발리더.
- 한재홍: agent-app/core/infra, 서비스 내부 AI의 실제 도구 호출·근거 수집·원인 분석·해결안.
- 김아름: voc-app/core/infra, 티켓·Agent 연동·리포트 화면, web, scenario-runner와 공통 실행 기반.
- Java 21, Spring Boot, Gradle 멀티모듈과 저장소에 고정된 버전을 사용한다.
- 각 PC에서 commerce·agent·voc 세 앱과 PostgreSQL, 구현된 web을 모두 실행할 수 있게 한다.
  특정 담당자의 PC가 켜져 있어야만 다른 PC의 로컬 시연이 가능한 구조로 만들지 않는다.
- 개발을 수행하는 Codex와 제품 내부에서 VOC를 조사하는 AI Agent를 구분한다.
  개발리더의 코드 수정 권한을 제품 Agent의 데이터 변경 권한으로 확대하지 않는다.

다른 PC의 실행 세션·인증·로컬 DB·대화 기억이 이 세션과 자동으로 공유된다고 가정하지 않는다.
세 담당자의 goal은 각 PC에서 시작되어 있어야 한다.

## 4. 필수 결과물

1. 주문·결제·쿠폰·재고·취소·환불 API와 실제 PostgreSQL 저장을 갖춘 커머스.
2. 일곱 VOC의 독립 초기화·시드·재현 요청·기대 관측값과 정상 대조 사례.
3. Agent가 읽을 수 있는 DB·구조화 로그·실행 소스 스냅샷·정상 업무 정책.
4. VOC 입력→실제 조사→근거 열람→원인·해결안 리포트의 통합 실행과 화면 검증 결과.
5. 다른 PC에서도 따라 할 수 있는 설치·기동·초기화·재현·검증 명령과 README.
6. 전체 코드 검토, 발견한 문제, 수정 커밋, 재검증을 연결한 리더 기록.
7. 실제 실행 산출물, 시연 화면 자료, 제출용 해커톤 보고서, 실제 개발 에이전트 세션 로그.
8. 최신 공유 내용에 유효한 세 담당자의 DONE과 리더 APPROVED.

화면·Agent·티켓의 기본 구현 책임은 해당 담당자에게 있다. 리더는 연동을 확인하고 누락·오류를 수정할 수 있다.
보고서의 계획 문장을 구현 완료 사실로 복사하지 않는다.

## 5. 커머스 구현과 의도한 결함

상품·재고 조회, 주문 생성·조회, 모의 결제, 쿠폰 적용, 전체 취소·모의 환불을 계약대로 구현한다.
정상 업무 기준은 demo-v1 정책이다. 금액·시간·상태·오류·식별자의 형식은 공통 계약을 따른다.
외부 실결제나 실고객 데이터 없이 합성 데이터와 모의 결제·환불 제공자를 사용한다.

| ID | 필수 재현 | 정상 대조의 예 |
| --- | --- | --- |
| VOC-01 | 간편결제 승인 후 주문 상태 갱신 누락 | 카드 결제의 정상 상태 전이 |
| VOC-02 | 최소 주문금액 50,000원과 같은 금액에 쿠폰 거절 | 49,999원 거절·50,001원 허용 |
| VOC-03 | 60,000원에 10% 쿠폰 적용 시 정수 나눗셈으로 할인 0원 | 정액 쿠폰 및 정책상 6,000원 할인과 대조 |
| VOC-04 | 같은 checkoutKey의 재시도로 주문 두 건 생성 | 다른 키로 생성한 별개의 정상 주문 |
| VOC-05 | 일시적인 환불 실패 이후 재처리 누락 | 장애 없는 환불 완료 |
| VOC-06 | 취소·환불 완료 후 유효한 쿠폰이 사용 상태로 남음 | 만료 쿠폰 재사용 거절 |
| VOC-07 | 재고 1개에 서로 다른 두 동시 주문이 모두 성공 | 충분한 재고 및 순차 요청의 정책상 결과 |

VOC-07은 실제로 독립된 DB 트랜잭션·연결을 사용한다. 두 요청이 재고를 확인한 다음 차감하도록
제한 시간이 있는 테스트용 동기화 지점을 제공하고 실패·종료 시 대기를 해제한다.
초기 재고, 성공 주문 수량, 최종 재고, 차감 이력을 실제 DB와 로그로 증명한다.
응답만 조작하거나 같은 트랜잭션 안의 순차 호출을 동시성 재현으로 기록하지 않는다.

이 일곱 결함은 조사·시연 대상이므로 보존한다. 다른 우발적 오류는 수정한다.
원인에 대한 해결안은 제시하되 취약 경로를 없애 시연을 깨뜨리지 않는다.
수정 전후 비교 버전은 기존 필수 범위를 끝낸 뒤 별도 범위로 다룬다.

## 6. 합성 데이터와 조사 근거

- fixtures/commerce/VOC-01부터 VOC-07까지 시드·초기화 SQL, 요청 README, expected.md를 제공한다.
- 데이터가 부족하면 실제 정책의 경계값을 포함한 합성 데이터를 만들고 ID·가정·생성 규칙을 기록한다.
  예시 프롬프트의 품목 20건을 그대로 목표로 삼지 말고 일곱 시나리오를 재현할 충분한 데이터를 만든다.
- 초기화는 해당 시나리오의 합성 데이터에 한정한다. 다른 앱·실행·기존 데이터에 영향을 주지 않는다.
  시나리오는 별도 데모 DB에서 순차 실행하고 VOC-07 내부 요청만 동시에 실행한다.
- requestId·orderId·productId·checkoutKey 등 계약의 식별자와 buildId로 API·DB·JSONL 로그를 연결한다.
  커밋되지 않은 업무 처리를 성공 로그로 남기지 않는다.
- 실행 중인 바이너리와 일치하는 소스 스냅샷·manifest를 제공한다. 최신 Git 소스를 실행 소스로 오인하지 않는다.
- 평가 정답·시드·테스트·재현 동기화 구현·제출 자료를 Agent의 조사 입력이나 소스 검색 범위에 넣지 않는다.
- Agent의 commerce DB 접근은 SELECT 전용이며 쓰기·DDL이 거절되는지 실제로 확인한다.
  Agent가 제안한 조치나 SQL을 운영 데이터에 자동 적용하지 않는다.

## 7. GitHub 변경 확인·반영·공유

원격 변경을 확인하는 것, 파일에 반영하는 것, 새 앱을 실행하는 것을 각각 수행한다.

1. 시작과 작은 작업 완료 시 ./scripts/dev status를 실행한다. 긴 구현 중에도 약 5분마다 확인한다.
   긴 빌드·다운로드가 진행 중이면 마친 직후 확인하며, 정확한 초 단위 실행을 보장한다고 기록하지 않는다.
2. status는 fetch 후 최근 다섯 커밋과 상태를 보여준다. 이것만 보고 전체 변경을 검토했다고 판단하지 않는다.
   마지막으로 검토한 원격 SHA와 이번에 fetch한 SHA를 고정해 그 사이 모든 커밋과 파일 차이를 읽는다.
   로컬 확인 지점은 Git에 올리지 않는 runtime 아래에 기록하고, 실제 검토 후에만 전진시킨다.
   첫 실행·확인 지점 유실 시 현재 코드·상태·계약을 검토해 기준을 다시 잡는다.
3. 미커밋 편집을 보존하고 자기 변경만 로컬 커밋한 뒤 깨끗한 main에서 ./scripts/dev sync를 실행한다.
   미공유 로컬 커밋은 최신 main 위에 통합하고, 충돌은 양쪽 의도와 계약을 확인해 해결한다.
4. 소스 반영 후 영향 범위를 검사하고 필요한 빌드·마이그레이션·앱 재기동·회귀 검증을 수행한다.
   세 앱의 buildId와 Agent가 조사하는 소스가 일치하는지 확인한다.
5. 보통 15~30분마다 검증 가능한 단위로 코드·계약·자기 상태를 커밋하고 ./scripts/dev publish로 공유한다.
   동기화→검증→세 앱 기동·연결 확인→일반 push의 실패를 해결한다.
   통합 후 예전 검증 결과를 그대로 사용하지 않는다.
6. 자기 DONE 후에도 약 60초마다 원격 변경과 요청을 확인한다. 변경이 없으면 비용이 큰 동일 검증을 반복하지 않는다.

./scripts/dev watch는 60초마다 fetch·상태 출력을 하는 열람 도구다. 파일 반영·앱 재기동·goal 재시작은 하지 않는다.
별도 watch 출력이 이 에이전트에게 자동 전달된다고 가정하지 말고 작업 루프에서 직접 상태를 읽는다.
강제 push·공유 이력 재작성·reset --hard·무단 stash/변경 삭제로 충돌을 없애지 않는다.

## 8. 담당자 간 요청과 인터페이스 변경

commerce 진행·요청은 docs/status/commerce.md, 리더 검토·지적은 docs/status/lead.md에 기록한다.
다른 담당자의 상태 문서와 실제 커밋을 확인하고 중복 구현을 피한다.

요청에는 추적 ID, 대상 역할, 필요한 동작·필드, 영향받는 API·DB·로그·화면, 재현 명령과 입력,
예상·실제 결과, 관련 커밋, 완료 확인 방법을 남긴다. 일반 요청은 COMMERCE-001 같은 ID,
리더 지적은 LEAD-001 같은 ID를 쓴다.
받은 요청은 자신의 상태에 같은 ID로 접수·구현 커밋·실제 검증·해결 상태를 기록한다.
GitHub에 요청을 올렸다는 사실만으로 상대가 읽고 구현했다고 간주하지 않는다.

계약 필드 제거·이름 변경은 소비자 영향과 전환 순서를 먼저 기록하고 양쪽 구현·문서·검증을 함께 맞춘다.
상대 작업이 지연되면 독립 구현·대조 사례·데이터·계약 검증을 계속한다.
리더가 다른 영역을 직접 수정하면 대상·이유·담당자의 진행 중 변경·검증·계약 영향을 공유한다.
타인의 DONE JSON은 대신 작성하지 않는다.

## 9. 구현 우선순위와 반복 방법

먼저 DDL·상품·재고·주문·추적 식별자와 VOC-07을 구현해 첫 통합을 연다.
재현 데이터·로그·소스를 두 담당자에게 전달하고, 결제·쿠폰·취소·환불과 VOC-01~06을 완성한다.
이후 실제 VOC→Agent→리포트를 연결하고 정상·예외·재시도·복구·화면 검증을 확장한다.

매 반복은 상태 확인→작은 구현→실행→관측값 확인→원인 수정→회귀 검증→기록·공유 순서로 한다.
합리적인 사소한 선택은 직접 결정하고 가정을 남긴다. 같은 실패를 그대로 무한 재시도하지 않는다.
사용자에게 중간 계획 승인이나 계속 진행할지를 반복해서 묻지 않는다.
구현 범위·완료 기준을 임의로 줄이지 않고, 불필요한 새 기능을 계속 추가해 종료를 늦추지도 않는다.

## 10. 기능·데이터·복구 검증

- 전체 빌드와 관련 단위·통합 검증을 통과하고, 세 앱의 실제 PostgreSQL·HTTP 연결을 확인한다.
- VOC-01~07은 독립 초기화 후 각각 최소 3회 성공적으로 재현한다.
  VOC-07의 동시성 재현은 총 최소 20회 실시하며 각 회의 주문·재고·이력 결과를 남긴다.
  이 횟수는 커머스 재현 기준이며 같은 횟수의 유료 모델 호출을 요구하지 않는다.
- 정상 대조, 빈 입력, 잘못된 숫자·수량, 경계 금액, 없는 ID, 정보 부족, 중복 요청을 검증한다.
- VOC 접수 재전송과 새 조사 요청의 키를 구분하고, 중복 실행·유실·잘못된 티켓 연결을 검사한다.
- 통신 오류·타임아웃·재시작 후 상태와 복구 경로를 확인한다. 실패를 성공처럼 표시하지 않는다.
- 일곱 결함의 의도된 실패와 시스템의 우발적인 오류를 구분한다.
  실제 DB·로그·실행 소스·화면·리포트가 같은 요청과 빌드를 가리키는지 확인한다.
- 테스트 삭제·skip·단언 약화, 실패 결과 삭제, 성공한 재실행만 선별하는 방법으로 통과시키지 않는다.
  원인이 해결되지 않은 간헐적 실패는 미해결 문제로 남긴다.

기동·health·smoke 통과를 업무 기능 완료로 쓰지 않는다. businessReady를 검증 없이 true로 바꾸지 않는다.
모의 LLM 결과는 개발 검증으로 표시하고 실제 모델 검증을 대체하지 않는다.

## 11. AI 조사 품질과 화면 검증

Agent가 실제로 선택·실행한 DB·로그·소스·정책 조회와 후속 모델 요청을 확인한다.
하드코딩한 원인·정답 파일·문의 키워드별 고정 응답으로 실제 조사를 대체하지 않는다.
보고서의 원인과 해결안은 실제 evidenceId, DB 식별자, 로그 위치, 소스 빌드·파일·줄 번호로 검토한다.
존재하지 않는 근거, 잘못된 인용, 정상 사례의 오진, 불확실한 원인의 단정은 실패로 처리한다.
정보가 부족하면 NEEDS_INPUT과 필요한 정보를, 실행 실패는 실제 실패 상태와 이유를 반환한다.
조사 COMPLETED와 문의 RESOLVED를 혼동하지 않는다.

리더는 실제 브라우저로 PC와 모바일 크기에서 문의 입력·접수·진행·결과·근거 열람·재조사를 확인한다.
빈 값·잘못된 입력·긴 문의·로딩·오류·정보 부족·재시도 상태를 확인하고 화면 증거를 보존한다.
화면 캡처만으로 API·DB 검증을 대체하지 않는다. 모바일 검증이 뷰포트 에뮬레이션이면 그렇게 기록한다.
실행 도구가 없어 수행하지 못한 검증을 수행한 것으로 쓰지 않는다.

## 12. 실제 모델, 사용 권한과 비용

[데모용 LLM 정책](../planning/demo-llm-policy.md)을 적용한다. 제공된 OpenAI 키는 서비스 데모 전용이며
개발 에이전트·코드 생성·일반 테스트·CI·자동 반복 평가에 사용하지 않는다.
기본 개발은 외부 유료 호출 없이 모의 모델·합성 응답으로 한다.
키가 존재한다는 이유로 up/check/publish/verify-mvp/role-done/lead-approve에서 유료 호출을 시작하지 않는다.

실제 모델 검증 전에 허용된 데모 제공자·모델·호출 수·최대 예상 비용·예산 공유 범위를 확인한다.
정의된 허용 범위 안에서 실행하고, 개발용 유료 호출은 별도 사용 범위·예산이 정해져 있어야 한다.
$30은 개발에 임의 사용 가능한 예산이 아니다. 데모 누적 예상 비용이 $30을 넘거나 가격·사용량을
확인할 수 없으면 새 유료 호출을 시작하지 않는다. 여러 PC가 각자 $30을 쓸 수 있다고 가정하지 않는다.
정책에 따른 영속 비용 예약·동시 호출·재시작·미확정 비용·차단 처리를 모의 모델로 검증한다.

로컬 LLM을 선택한 경우 실제 제공자·모델·실행 결과를 구분해 기록하고 OpenAI로 자동 전환하지 않는다.
모의 결과를 live로 표기하거나 완료 도구를 우회하지 않는다.
실제 모델 검증의 허용 범위·인증이 준비되지 않았으면 독립 구현과 모의 검증을 계속하고,
필수 실제 검증은 미검증으로 남긴다. 그것만 남으면 차단 사유를 공유하며 DONE·APPROVED·goal 완료를 선언하지 않는다.

## 13. 개발리더의 독립 검토·수정

세 담당자의 유효한 DONE은 ./scripts/dev roles-check로 확인한다. 이것은 최종 검토의 시작 조건이다.
내 commerce 코드를 포함해 commerce·agent·voc·web·scenario-runner/fixtures·실행 기반·계약을 직접 읽는다.
마이그레이션, 트랜잭션, 동시성, 멱등성, 오류 처리, 재시도·복구, 도구 권한, 근거 연결, 비용 제어와 테스트를 검사한다.

다른 담당자의 성공 로그만 재사용하지 않고 내 PC에서 실제 앱·DB·모델·화면의 전체 흐름을 새로 검증한다.
문제는 LEAD ID·역할·파일·재현·예상/실제 결과로 기록하고 모든 모듈에서 직접 수정·보완할 수 있다.
수정 후 관련 회귀 검증과 통합 검증을 수행한다. 코드가 바뀌면 각 담당자가 최신 코드의 DONE을 갱신해야 한다.

docs/status/lead-review.json은 실제 검토한 커밋·내용 해시·파일·판단 근거,
필수 검사·반복 재현 결과·지적 해결과 재검증을 기록한다. 검토하지 않은 영역에 PASSED를 쓰지 않는다.
알려진 미해결 결함·미처리 필수 요청·불안정한 재현·필수 검증 누락이 있으면 승인하지 않는다.

## 14. 기록·제출 자료·실제 세션 로그

작업 시작부터 실행 명령, 시각·종료 코드, 실제 결과, 실패·수정, 커밋·buildId·모델 정보를 남긴다.
Git에서 제외된 runtime/submission 아래에 세션 로그·명령 출력·검증 결과·스크린샷을 구분해 보존하고
파일 목록·실행 환경·관련 커밋을 적은 manifest를 둔다. 실행마다 별도 파일로 보존해 실패 기록을 덮어쓰지 않는다.
이 자료는 Agent가 VOC를 조사할 때 읽는 근거 디렉터리와 분리한다.

개발 에이전트의 실제 세션 로그는 현재 세션에서 접근 가능한 원본 또는 실행기가 제공하는 공식 내보내기로 확보한다.
제품 Agent의 도구 실행 로그와 개발 세션 로그를 구분한다. 요약문을 실제 세션 원본이라고 부르거나 대화를 재구성하지 않는다.
자동 내보내기가 제공되지 않으면 확보한 범위와 누락을 기록하고 제출에 필요한 최소 조치를 명시한다.
원본과 마스킹한 제출본을 구분하고 API 키·토큰·개인정보·관계없는 세션 내용은 공유하지 않는다.
Git에는 코드·합성 입력·설정 예제·비밀 값 없는 검증 요약을 공유한다. 원본 실행 로그나 .env는 push하지 않는다.

README와 docs/hackathon-report.md에 실제 구현 범위, 구조, 실행 방법, 일곱 재현,
시나리오별 성공·실패·근거·해결안 평가, 시연 순서, 한계와 산출물 위치를 반영한다.
응답 시간과 품질은 실제 측정한 값만 쓴다. 사람의 수동 조사·후속 검토 시간을 측정하지 않았다면
미측정으로 남기고 시간 절감률을 만들어내지 않는다. 예측·가정·실측을 구분한다.
화면 자료는 실제 앱을 실행해 만든다. 배포나 녹화를 하지 않았다면 존재하는 URL·영상처럼 작성하지 않는다.

## 15. 사전 허용 범위와 외부 의존성

프로젝트의 코드·문서·합성 데이터·의존성 준비·로컬 실행·검증·오류 수정,
지정된 GitHub 저장소 main의 일반 commit·fetch·sync·push는 이미 허용된 범위에서 진행한다.
리더는 전체 모듈의 문제를 수정할 수 있다. 매번 사용자에게 계획이나 같은 권한을 다시 묻지 않는다.

기존 작업·데이터는 보존한다. 실고객·실결제·운영 시스템 연결, 기존 비합성 데이터 삭제,
별도 허용 범위 밖의 유료 사용이나 외부 배포·전송은 이미 승인되었는지 확인하고, 없으면 필요한 사항만 요청한다.
데모는 [ngrok 로컬 실행](../ngrok-local-demo.md)을 기준으로 web·세 앱·DB를 같은 PC에서 실행한다. web 한 곳만 공개하고 Agent는 OpenAI API를 직접 호출한다. web·접근 제어·ngrok 계정이 준비되면 공개 URL의 전체 흐름을 검증하며 로컬 smoke와 실제 데모 성공을 구분한다.
저장소 지침으로 실행 환경의 sandbox·인증·조직 정책을 우회하지 않는다.

인증·모델 허용 범위·다른 PC의 실행처럼 직접 해결할 수 없는 조건은 만들거나 완료됐다고 가정하지 않는다.
시도한 작업·실패 원인·남은 독립 작업·꼭 필요한 외부 조치를 상태 문서에 남긴다.
독립 작업을 모두 마치고 같은 외부 차단으로 더 진행할 수 없으면 goal 실행기의 blocked 규칙을 따른다.
사용자가 명시적으로 중단하면 중단한다. 세션·PC·네트워크·사용량 제한과 무관하게 영구 실행된다고 약속하지 않는다.

## 16. 완료 기록과 최종 종료 순서

구현·데이터·필수 문서·제출 자료를 검증하고 공유한다. 일반 실행·공유 명령은 다음과 같다.

```bash
./scripts/dev status
./scripts/dev sync
./scripts/dev up
./scripts/dev smoke
./scripts/dev check
./scripts/dev publish
```

각 명령은 현재 상태에 맞춰 실행한다. sync/publish는 깨끗한 커밋 경계에서 사용한다.
통과한 고비용 검증을 변화나 의심 근거 없이 연달아 반복하지 않는다.
아래 실제 모델 검증 명령은 12절의 허용 범위와 인증·비용 제어가 준비된 경우에만 실행한다.

1. ./scripts/dev role-done commerce로 실제 MVP를 검증하고 생성된 내 완료 JSON을 커밋·publish한다.
2. 다른 담당자의 변경·요청·완료 갱신을 확인하며 작업을 계속한다. 타인의 DONE을 대신 작성하지 않는다.
3. ./scripts/dev roles-check로 세 유효한 DONE을 확인하고 리더의 독립 검토·수정·재검증을 마친다.
4. lead.md와 lead-review.json을 사실대로 작성해 커밋·publish한다.
5. ./scripts/dev lead-approve로 새 전체 검증을 수행하고 생성된 lead.json을 커밋·publish한다.
6. 마지막으로 깨끗하고 완전히 동기화된 main에서 ./scripts/dev team-check를 실행한다.

코드·테스트·시드·설정·계약·완료 기준 등 docs/status 밖의 추적 내용이 바뀌면 기존 DONE은 무효가 된다.
최종 README·보고서 변경도 이 규칙을 따른다. 수정 후 해당 코드에 대한 완료를 다시 갱신한다.
역할별 완료 JSON이나 리더 검토 기록 변경은 기존 리더 승인도 무효화한다.
새 문제를 발견하면 role-reopen commerce 또는 lead-reopen으로 내 선언을 철회하고 수정·재검증한다.
상태 디렉터리에 코드나 검증 기준을 옮기거나 결과 JSON을 꾸며 판정을 우회하지 않는다.

## 17. 반드시 함께 충족할 완료 기준

- 정해진 모든 필수 기능·산출물이 있고 실제 앱·데이터·근거·화면·모델로 전체 흐름이 동작한다.
- 일곱 결함의 독립 반복 재현과 정상·경계·잘못된 입력·정보 부족·중복·복구 검증을 통과했다.
- 의도한 결함 외에 알려진 미해결 문제·원인 미해결의 간헐적 실패·필수 연동 요청·필수 검증 누락이 없다.
- 세 담당자의 유효한 DONE과 리더의 독립 검토에 근거한 APPROVED가 GitHub main에 공유됐다.
- 로컬 미커밋·미공유·미반영 원격 변경이 없고 마지막 team-check의 종료 코드가 0이다.
- 실행 방법, 실제 검증·실패와 수정 기록, 보고서·시연 자료·실제 세션 로그의 확보 범위가 정리됐다.
  필수 제출 자료가 누락됐다면 팀 상태 검사만으로 완료하지 않는다.

기능이 돌아가는 것처럼 보이거나 세 사람이 완료라고 말한 것만으로 종료하지 않는다.
2일이 지났거나 예상 시간이 소진됐다는 이유로 완료를 선언하지 않는다.
정한 범위의 검증을 충족한다는 뜻으로 완료하며, 모든 미래 입력에서 오류가 없다는 보장은 하지 않는다.
team-check 성공 후라도 이미 아는 미해결 필수 문제가 있으면 선언을 철회하고 계속 작업한다.

## 18. 진행 전달과 최종 보고

진행 중에는 완성한 기능, 실제 검증 결과, 발견한 문제, 다음에 확인할 것을 짧게 알린다.
긴 작업의 대화 맥락이 바뀌어도 상태 문서·커밋·실행 기록을 읽고 남은 작업을 이어간다.
계획 제시나 중간 성공 보고로 goal을 끝내지 않는다.

완료 시 다음을 간단히 보고한다.

1. 완성한 기능과 세 앱·화면의 실행 방법.
2. 마지막 공유 커밋, 세 DONE·리더 APPROVED와 team-check의 실제 결과.
3. 일곱 시나리오의 반복 횟수·결과, 정상·예외·복구·PC·모바일 검증.
4. 실제 모델·사용 범위·비용 기록과 근거·리포트 검토 결과.
5. 코드, 합성 데이터, README, 보고서, 시연 자료, 실제 세션 로그의 위치.
6. 필수 범위 밖의 한계와 미측정 항목. 수행하지 않은 검증을 완료했다고 쓰지 않는다.

막혔거나 사용자가 중단했다면 완료 보고 대신 실제 진행 상태·차단 사유·재개에 필요한 조건을 남긴다.
