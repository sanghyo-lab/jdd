논의가 필요한 내용은 이 폴더에 건별 Markdown으로 작성하고, **각 작업자가 같은 건의 문서에 직접 답변**한다.
이 README는 답변을 근거로 갱신하는 목록이다. 상세 제안·답변·검증의 원본은 건별 문서다.
역할별 상태에는 논의 ID와 링크를 남긴다. Issue가 있으면 연결하되 답변을 두 곳에서 따로 관리하지 않는다.

## 작성 규칙

1. 목록과 기존 문서를 검색해 중복 논의 없이 같은 건에 이어 쓴다.
2. TEMPLATE.md를 복사해 `DISC-YYYYMMDD-<role>-NNN-<short-topic>.md`로 만든다.
   role은 commerce, agent, voc 중 작성자 역할이고 리더 겸임은 commerce를 쓴다.
   예: `DISC-20260921-voc-001-api-error.md`. ID는 파일명 앞부분이며 작성일·역할별 번호로 충돌을 줄인다.
3. 제목·ID·제안 버전·작성자·정리 담당·영향받는 역할·필수 합의자·상태·생성/갱신 시각을 채운다.
   시각에는 시간대를 포함한다. 정리 담당은 기본적으로 작성자이며 변경 시 인계 답변을 남긴다.
4. 결정할 질문, 배경과 원문/커밋, 재현 입력/명령과 기대/실제, 권고안·대안·영향,
   현재 계약, 해소 기준, 대기 중 독립 작업을 구체적으로 쓴다. 적용되지 않는 항목은 이유와 함께 해당 없음으로 쓴다.
5. 사실·추론·제안을 구분한다. API 키·개인정보·실제 원본 로그 대신 합성 입력과 안전한 근거를 사용한다.
6. 건별 문서와 README 행·집계를 같은 커밋에 넣고 검증 후 즉시 main에 publish한다.
   자신의 변경 경로를 명시해 add하며 기존 사용자 변경은 포함하지 않는다.
   논의·답변만 바꾼 단위는 [협업 문서 공유 절차](../autonomous-development.md#협업-문서만-공유할-때)로 문서 검증 후 즉시 일반 push한다.

## 확인과 답변

- commerce·agent·voc 전원은 시작·작은 작업 완료 때와 긴 작업 중 약 5분마다 fetch한 목록과 새 답변을 읽는다.
  리더 관련 건은 이상효가 commerce 또는 lead 자격을 명시한다. 다른 PC의 자동 실행을 가정하지 않는다.
- 각자 해당 문서의 자기 역할 답변 구역에 시각·작성자·검토한 제안 버전(P1 등)과 의견을 추가한다.
  수락·조건부 수락·수정 제안·반대·정보 요청·영향 없음·검증 결과 중 의견을 분명하게 표현한다.
- 단순히 읽었다는 답변 대신 근거, 필요한 변경, 담당 행동과 검증 기준을 남긴다.
  관련이 없으면 영향 없음과 이유를 답변한다. 필수 합의자가 영향 없음으로 빠지려면 정리 담당이 영향 범위를 재확인한다.
- 답변을 쓴 사람이 README의 답변 대기자·다음 행동·갱신 시각과 건별 요약을 같은 커밋에서 갱신한다.
  새 답변을 반영해도 조건이나 반대가 남으면 해소로 바꾸지 않는다.
- 다른 사람의 답변은 덮어쓰거나 대필하지 않는다. 정정도 새 답변으로 이전 기록을 지목한다.
  제안이 실질적으로 바뀌면 P2처럼 버전을 올리고 변경점을 남긴다. 이전 버전의 수락을 새 합의로 재사용하지 않는다.
- 건별 문서와 README는 공동 편집한다. 다른 역할의 상태 문서·완료 JSON은 기존 소유 규칙을 유지한다.

## 상태와 해소 판정

| 상태 | 의미 | 목록에 표시할 내용 |
| --- | --- | --- |
| OPEN | 제안 등록, 확인·답변 대기 | 답변할 역할과 질문 |
| DISCUSSING | 조건·이견·추가 정보가 남음 | 남은 쟁점과 다음 답변자 |
| BLOCKED | 외부 입력·선행 작업 대기 | 실제 차단 사유와 해제 조건 |
| AGREED | 최신 제안에 합의, 실행·문서 반영·검증은 남음 | 실행 담당과 남은 기준 |
| RESOLVED | 최신 합의와 건별 해소 기준을 모두 확인함 | 결정 요약·답변 위치·검증/공유 커밋 |
| REOPENED | 해소 후 새 실패·요구 변경 발견 | 다시 연 근거·제안 버전·대기자 |

정리 담당 또는 문서에 위임받은 작업자가 다음을 확인하고 해소 기록을 작성한다.

1. 세 작업자의 확인 답변이 있고 최신 제안의 필수 합의자가 명시적으로 수락했다.
   조건부 수락은 조건의 충족을 확인해야 한다. 침묵·시간 경과·자기 판단만으로 합의하지 않는다.
2. 미해결 반대·질문이 없고 최종 결정·적용 순서·책임자가 기록돼 있다.
3. 문서 결정만 필요한 건은 필요한 계약/정책 문서에 반영하고 링크 검증과 공유 근거를 남겼다.
   구현·연동 변경이 필요한 건은 합의만으로 닫지 않고 실제 코드·관련 검증·소비자 확인까지 기록했다.
4. 건별 상태·갱신 시각·해소 기록과 README 행·집계·대기자·해소 근거를 함께 맞췄다.
   현재 작성 중인 커밋 SHA를 지어내지 않는다. 기존 답변·검증 커밋과 문서 내 근거를 연결하고 Git 이력으로 공유 여부를 확인한다.

새 실패나 누락을 발견한 작업자는 즉시 REOPENED로 바꾸고 이유를 남긴다.
목록과 본문이 다르면 실제 답변·검증을 대조해 바로잡고, 불확실하면 미해소로 유지한다.
동시 push 충돌은 모든 답변과 서로 다른 행을 보존해 합치고 집계를 다시 계산한다.

## 검증과 팀 완료 연결

- 제안·답변마다 링크와 목록/본문의 ID·상태·대기자·근거·건수를 확인하고 즉시 main에 커밋·publish한다.
- 기존 상태·Issue에서 답변하던 건은 건별 문서를 연결한 뒤 새 답변을 이곳에 모은다.
  역할 상태에는 자기 접수·구현·검증 결과를 요약한다. 리더 지적은 lead-review.json에도 연결한다.
- 미해소 필수 논의는 [팀 완료 기준](../team-completion.md)의 미처리 연동 요청·알려진 문제로 추적한다.
  해소 표시나 미해소 0건은 역할 DONE·리더 APPROVED·team-check를 대신하지 않는다.
- 이 폴더는 docs/status 밖의 추적 내용이므로 변경되면 기존 완료 기록의 내용 해시가 달라진다.
  완료 판정을 우회해 제외하지 않는다. 최종 실제 검증 전에 논의·답변·해소 기록까지 공유한다.
- README는 자동 생성 파일이 아니다. 각 개발 작업자가 답변과 함께 갱신한다.
  5분 예약은 새 논의·답변·목록 불일치를 확인해 개발 작업에 전달하며 타인의 답변이나 해소 근거를 만들지 않는다.
