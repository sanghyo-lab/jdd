## 결정할 질문

QUEUED를 기본 최대 20건·10분으로 제한하고, 미접수 과부하를 HTTP 429로 구분해 같은 키로 제한 재전송하는 P1을 적용할 것인가?

## 배경과 확인 근거

- [구현 프롬프트](../prompts/implement-voc-investigation-agent.md) §3과 [비용 계획](../planning/llm-efficiency-plan.md) §5는 QUEUED 대기/수용량과 RUNNING 예산을 구분하도록 요구한다.
- `6e240ab`의 실제 코드를 대조했다. worker는 기본 동시 2개·RUNNING 3분을 제한하지만 JdbcInvestigationRepository는 QUEUED 수용량/만료 없이 접수하며 실행 저장소의 expire는 RUNNING만 처리한다. 따라서 오래 대기한 요청이 나중에 모델을 실행할 수 있다. 과부하 HTTP 검증은 아직 수행하지 않았다.
- [v1 계약](../integration-contract.md)은 같은 키 재전송·입력 충돌·FAILED/INVESTIGATION_TIMEOUT을 이미 제공한다. 새로운 접수 429 코드와 소비자 재전송 규칙은 합의가 필요하다.

## P1 제안과 대안

- 새 접수의 대기 만료 시각을 createdAt + 설정값으로 영속 저장한다. 기본 10분, 유효 범위 1초~1시간이다. 재전송·재시작·설정 변경으로 기존 기한을 연장하지 않는다. 과거 행은 기존 createdAt + 10분으로 이관한다.
- worker는 실행 슬롯이 모두 차 있어도 만료된 QUEUED를 FAILED/INVESTIGATION_TIMEOUT/retryable=false로 종료한다. message는 대기 시간 초과를 명시하며 report=null, 같은 ID·입력·기존 근거를 보존한다. 선점 쿼리도 만료 행을 제외해 정리와 경쟁하더라도 유료 실행을 시작하지 않는다. 새 공개 상태·필수 DTO 필드는 추가하지 않는다.
- RUNNING의 3분은 실제 선점 시각부터 별도 계산한다. 대기 시간이 RUNNING 예산을 소비하거나, 새 실행 예산 때문에 대기 만료가 연장되지 않는다. DB/worker가 꺼진 동안 상태 갱신은 불가능하지만 복구 후 만료된 요청은 실행하지 않는다.
- **합의 후 접수 수용량:** 기본 QUEUED 20건, 설정 범위 1~100건. DB에서 접수 원자성을 보장해 동시 요청이 상한을 넘지 않게 한다. RUNNING은 기존 worker 동시성으로 따로 제한한다.
- 수용량 초과의 새 입력은 HTTP 429/INVESTIGATION_QUEUE_FULL/retryable=true와 Retry-After: 5를 반환한다. 조사·모델 예약은 생성하지 않는다. 이미 받은 같은 키는 가득 찼어도 기존 ID/상태를 반환하고 다른 입력이면 기존 409를 유지한다.
- VOC는 이 429를 submissionError로 처리하며 조사 FAILED로 꾸미지 않는다. 같은 저장 입력·같은 키로 최대 3회, Retry-After 이상 간격의 backoff(예: 5/10/20초 + jitter) 후에도 전달되지 않으면 수동 동일 키 재전송을 안내한다. 새 키를 자동 생성하지 않는다.
- 이미 접수된 조사 polling은 기본 대기 10분 + 실행 3분을 감안한다. 예시 관측 한도 14분과 최대 5초 간격을 소비자 설정으로 맞춘다. polling이 끝나거나 화면을 새로고침해도 실제 조사를 실패/재실행으로 바꾸지 않는다.
- 대안: 항상 202로 받은 뒤 초과 요청을 실패시키면 저장량 증가와 접수/조사 실패 혼동이 남는다. 무제한 큐는 오래된 요청의 뒤늦은 유료 실행을 허용하므로 채택하지 않는다.
- 적용 순서: 기존 오류 계약으로 대기 만료·선점 배제·복구를 독립 구현/검증 → 소비자 직접 합의 → 접수 429/수용량·계약·VOC 처리 연결 → 실제 HTTP/DB 모의 과부하 검증. 합의 전 새 429 동작을 공개하지 않는다.
