# 세 PC의 goal 협업 규칙

각 PC의 goal이 하나의 담당 역할을 구현한다. GitHub main은 소스·계약·상태를 공유하는 기준이며,
각 에이전트의 대화 기억·로컬 DB·실행 로그는 다른 PC로 자동 전달되지 않는다.
시작 방법은 [역할별 goal 안내](goals/README.md), 실행 방법은 [로컬 개발 안내](local-development.md)를 따른다.

## 반복과 동기화

1. 시작할 때와 작은 작업을 끝낼 때 원격 main의 커밋·세 상태 파일·계약 변경을 읽는다.
2. 긴 구현 중에도 약 5분마다 fetch해서 변경을 파악한다. watch는 알림·열람용이며 소스 파일을 교체하지 않는다.
3. 자기 변경을 로컬 커밋한 뒤 sync한다. 로컬 미공유 커밋이 있으면 새 main 위에 rebase한다.
4. 상대 변경을 반영해 구현·테스트하고, 보통 15~30분마다 공유 가능한 단위를 만든다.
5. 자기 상태 파일에 변경·검증·필요한 연동을 기록하고 명시적인 파일 목록으로 커밋한다.
6. publish는 sync→check→세 앱 재기동→실제 연결 검사→일반 push를 수행한다.
   동시 push 경쟁이면 최대 3회 최신 코드를 반영하고 매번 재검증한다.
7. 충돌은 개발 에이전트가 양쪽 변경과 계약을 읽어 해결한다. 충돌을 자동 삭제하거나 강제 push하지 않는다.

이 주기는 goal의 작업 지침이며 저장소가 꺼진 PC나 종료된 에이전트를 자동으로 시작하는 스케줄러는 아니다.
GitHub 원격 변경 확인과 로컬 파일 변경을 분리해 편집 중 파일을 덮어쓰지 않는다.
처음에는 위 시간 간격을 기준으로 하고, 큰 다운로드·빌드 중에는 검증을 마친 다음 공유한다.

## 담당자 간 요청

각자 docs/status/<role>.md만 갱신한다. 세 파일을 매 반복 읽는다.
상대 구현이 필요하면 자기 파일에 아래 정보를 남긴다.

- 요청 대상: commerce / agent / voc
- 필요한 API·필드·동작과 관련 계약
- 실행한 명령·입력, 예상·실제 결과
- 현재 제공 가능한 기능과 코드 커밋
- 이 요청 없이 진행할 수 있는 다음 작업

하나의 공통 상태 파일을 세 사람이 동시에 편집하지 않는다.
API 제공자는 요청을 읽고 호환 구현을 반영한 뒤 자신의 상태에 전달 결과를 기록한다.
공통 파일은 기본적으로 김아름이 유지하고 다른 담당자는 필요한 최소 변경과 영향을 기록한다.
매 변경마다 사람의 중간 승인을 받는 절차는 두지 않는다.

## 완료와 정체

역할별 기능 완료와 전체 통합 완료를 구분한다. 자신의 기능을 완료해도 실제 상대 API로 연결한 검증을 남긴다.
기동 상태만으로 업무 API나 AI 분석이 완성됐다고 판단하지 않는다.
현재 골격의 verify-mvp는 업무 준비 상태가 false이므로 실패하는 것이 정상이며,
scenario-runner도 미구현을 알리고 실패 종료한다.

실제 최종 검증에는 VOC-01~07, 정상, 정보 부족, 중복 요청, 통신·재시작 복구가 포함된다.
실제 모델명과 해당 buildId의 결과를 기록하고 평가 정답을 Agent 입력으로 사용하지 않는다.
종료 조건은 각 goal 문서의 기능·연동·검증·원격 공유를 모두 만족하는 것이다.

상대의 선행 구현이 늦으면 독립 기능·대조 사례·계약 테스트·문서를 계속 진행한다.
모델 인증·계정 권한처럼 에이전트가 만들 수 없는 외부 입력만 남으면 실제 차단 사유를 기록한다.
무기한 같은 실패를 재시도하거나 결과를 만들어 완료 처리하지 않는다.

## Codex 적용 방식

프로젝트 루트의 AGENTS.md는 저장소 공통 지침이다. 새 세션이 이 파일을 읽도록 각 PC에서 프로젝트를 연다.
기존 세션에는 최신 파일을 다시 읽도록 goal 시작문에 포함한다. [OpenAI 공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
goal의 최초 시작과 PC별 인증·실행 권한 준비가 끝나면, 위 반복을 각 세션이 독립적으로 수행한다.
