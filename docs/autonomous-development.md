# 세 PC의 goal 협업 규칙

각 PC의 goal이 담당 앱을 구현한다. 이상효는 commerce와 개발리더를 겸한다. GitHub main은 소스·계약·상태를 공유하는 기준이며,
각 에이전트의 대화 기억·로컬 DB·실행 로그는 다른 PC로 자동 전달되지 않는다.
시작 방법은 [역할별 goal 안내](goals/README.md), 실행 방법은 [로컬 개발 안내](local-development.md)를 따른다.
모든 역할의 goal은 [GitHub의 세 담당자 완료 기준](team-completion.md)을 함께 적용한다.

## 반복과 동기화

1. 시작할 때와 작은 작업을 끝낼 때 원격 main의 커밋·세 담당자와 리더 상태·계약 변경·논의 목록과 새 답변을 읽는다.
2. 긴 구현 중에도 약 5분마다 fetch해서 변경을 파악한다. watch는 알림·열람용이며 소스 파일을 교체하지 않는다.
3. 자기 변경을 로컬 커밋한 뒤 sync한다. 로컬 미공유 커밋이 있으면 새 main 위에 rebase한다.
4. 상대 변경을 반영해 구현·테스트하고, 검증 가능한 작업 단위가 끝날 때마다 즉시 커밋·publish한다. 시간 주기를 기다리지 않는다.
5. 자기 상태 파일에 변경·검증·필요한 연동을 기록하고 명시적인 파일 목록으로 커밋한다.
6. publish는 sync→check→세 앱 재기동→실제 연결 검사→일반 push를 수행한다.
   동시 push 경쟁이면 최대 3회 최신 코드를 반영하고 매번 재검증한다.
7. 충돌은 개발 에이전트가 양쪽 변경과 계약을 읽어 해결한다. 충돌을 자동 삭제하거나 강제 push하지 않는다.

이 주기는 goal의 작업 지침이며 저장소가 꺼진 PC나 종료된 에이전트를 자동으로 시작하는 스케줄러는 아니다.
GitHub 원격 변경 확인과 로컬 파일 변경을 분리해 편집 중 파일을 덮어쓰지 않는다.
큰 다운로드·빌드 중에는 필요한 검증을 마친 다음 해당 단위를 바로 공유한다.

status는 최근 다섯 커밋만 출력한다. 마지막으로 검토한 원격 SHA와 이번 fetch의 SHA 사이 전체 커밋·파일 차이를
별도로 읽어 변경이 많은 경우에도 누락하지 않는다. 로컬 확인 지점은 Git에서 제외된 runtime 아래에 기록하고
검토를 마친 뒤 갱신한다. 처음 시작하거나 기록이 없으면 현재 코드·계약·상태를 읽어 기준을 정한다.
이 기록은 각 에이전트가 관리하는 작업 지침이며 status/watch에 자동 검토 기능이 구현됐다는 뜻은 아니다.
소스를 반영한 뒤에는 영향받는 빌드·마이그레이션·앱 재기동·회귀 검증을 수행하고 실행 buildId를 확인한다.

## 담당자 간 요청

역할 상태와 완료 선언은 각자 docs/status/<role>.md와 자기 완료 JSON에만 작성한다. 세 담당자의 파일을 매 반복 읽는다.
논의가 필요한 요청은 [논의 목록과 규칙](discussions/README.md)에 따라 건별 문서를 만들고 자기 상태에서 연결한다.
상대 구현이 필요한 요청에는 아래 정보를 남긴다.

- 요청 대상: commerce / agent / voc
- 필요한 API·필드·동작과 관련 계약
- 실행한 명령·입력, 예상·실제 결과
- 현재 제공 가능한 기능과 코드 커밋
- 이 요청 없이 진행할 수 있는 다음 작업

역할별 상태 파일은 담당자가 유지한다. 예외로 docs/discussions의 건별 문서와 README는 공동 편집하며 모든 작업자가 해당 건에 직접 답변한다.
답변한 작업자가 같은 커밋에서 README의 상태·답변 대기·해소 근거·집계를 갱신한다. 상세 판정은 논의 규칙을 따른다.
API 제공자는 요청을 읽고 호환 구현을 반영한 뒤 건별 문서에 검증 결과를 회신하고 자기 상태에도 요약한다.
논의에는 DISC ID를 붙이고 기존 COMMERCE-001 등의 요청 ID가 있으면 함께 연결한다.
접수·합의·구현·검증 완료를 구분하며 필요한 답변과 실제 해소 기준이 충족되어야 RESOLVED로 갱신한다.
요청을 push한 것과 상대가 수신·조치한 것을 구분하고 실제 상태 응답과 커밋으로 확인한다.
공통 파일은 기본적으로 김아름이 유지하고 다른 담당자는 필요한 최소 변경과 영향을 기록한다.
매 변경마다 사람의 중간 승인을 받는 절차는 두지 않는다.
개발리더는 [리더 역할](roles/lee-sanghyo-lead.md)에 따라 모든 영역을 직접 검사·수정할 수 있다.
리더 지적은 LEAD ID와 대상 역할·재현 근거·수정·재검증 결과를 lead.md와 lead-review.json으로 공유한다.
담당자는 리더 요청을 확인하고 수정하거나 리더의 수정 결과를 반영해 자기 완료를 갱신한다.

## 완료와 정체

역할별 기능 완료와 goal 종료를 구분한다. 자신의 기능을 완료해도 실제 상대 API로 연결한 검증을 남긴다.
기동 상태만으로 업무 API나 AI 분석이 완성됐다고 판단하지 않는다.
현재 골격의 verify-mvp는 업무 준비 상태가 false이므로 실패하는 것이 정상이며,
scenario-runner도 미구현을 알리고 실패 종료한다.

실제 최종 검증에는 VOC-01~07, 정상, 정보 부족, 중복 요청, 통신·재시작 복구가 포함된다.
실제 모델명과 해당 buildId의 결과를 기록하고 평가 정답을 Agent 입력으로 사용하지 않는다.
각자 역할 조건과 실제 통합 검증을 통과하면 role-done <role>로 검증 결과를 기록하고 GitHub main에 공유한다.
세 담당자의 유효한 DONE은 roles-check로 확인하는 리더 최종 검토의 시작 조건이다.
이상효는 자기 PC에서 전체 코드를 검사하고 실제 통합 검증을 새로 실행해 문제를 수정·보완한다.
모든 goal의 종료 조건은 세 유효한 DONE과 리더의 유효한 APPROVED를 GitHub에 모두 공유하는 것이다.
`./scripts/dev team-check`가 성공하기 전에는 자기 역할이 끝나도 goal을 complete로 처리하지 않는다.
먼저 끝난 역할은 약 60초마다 원격 변경·연동 요청을 확인하고 필요한 수정·검증을 계속한다.
변경이 없으면 불필요한 새 기능이나 같은 고비용 검증을 반복하지 않는다.
코드·설정·계약·완료 기준이 바뀌면 오래된 DONE은 STALE로 제외되며 재검증 후 갱신한다.
문제가 발견되면 role-reopen <role>로 자기 DONE을 철회하고 이유를 공유한다.
리더는 lead-reopen으로 최종 승인을 철회한다. 코드·검토 기록·역할별 완료 JSON이 바뀌면 리더 승인도 다시 필요하다.

상대의 선행 구현이 늦으면 독립 기능·대조 사례·계약 테스트·문서를 계속 진행한다.
모델 인증·계정 권한처럼 에이전트가 만들 수 없는 외부 입력만 남으면 실제 차단 사유를 기록한다.
무기한 같은 실패를 재시도하거나 결과를 만들어 완료 처리하지 않는다.

## Codex 적용 방식

프로젝트 루트의 AGENTS.md는 저장소 공통 지침이다. 새 세션이 이 파일을 읽도록 각 PC에서 프로젝트를 연다.
기존 세션에는 최신 파일을 다시 읽도록 goal 시작문에 포함한다. [OpenAI 공식 AGENTS.md 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)
goal의 최초 시작과 PC별 인증·실행 권한 준비가 끝나면, 위 반복을 각 세션이 독립적으로 수행한다.
