# 한재홍 — 근거를 조사하는 AI Agent

## 1. 만들 결과

VOC 문의와 조사 대상 정보를 받아 이커머스 소스코드·로그·DB·업무 정책을 조회하고, 원인 후보와 해결방안을 근거와 함께 반환하는 애플리케이션을 만든다. 조사 접수·진행·보고서 API는 김아름이 연동한다.

[상세 구현 프롬프트](../prompts/implement-voc-investigation-agent.md)를 필수 기준으로 읽는다.
한재홍은 서비스 내부에서 실행되는 AI까지 구현한다. 서버의 LLM API 연결과 서비스 시스템 프롬프트,
모델의 반복 도구 호출, 실제 근거 저장, 보고서 검증·반환이 담당 범위다.
개발용 오케스트레이션의 검토 결과나 조사 접수 API만으로 서비스 AI가 구현됐다고 판단하지 않는다.

| 항목 | 담당 범위 |
| --- | --- |
| 실행 앱 | `agent-app`, 기본 포트 `8081` |
| 조사 로직 | `agent-core`: 조사 흐름, 도구, 근거, 리포트 |
| 조회·저장 | `agent-infra`: 커머스 SELECT, 로그·소스·정책 읽기, `agent` 스키마 |
| AI 연결 | Spring AI, 선택한 모델 제공자의 도구 호출 |
| 진행 기록 | `docs/status/agent.md` |

## 2. 구현할 기능

| 기능 | 구현 내용 |
| --- | --- |
| 조사 접수 | 입력 스냅샷·요청 키 저장, 조사 ID 발급, 비동기 실행 |
| 조사 흐름 | 문의의 대상을 찾고 필요한 도구를 호출해 추가 증거 수집 |
| 서비스 모델 실행 | 별도 LLM API 설정·연동, 버전이 있는 시스템 프롬프트, 도구 요청·결과·후속 모델 호출 연결 |
| 근거 수집 | 실제 반환 데이터에 근거 ID와 원문 출처 부여 |
| 리포트 생성 | 확인된 사실, 원인 후보, 해당 건 조치, 재발 방지, 부족한 정보 구조화 |
| 진행·결과 조회 | 조사 상태, 도구 실행 요약, 근거 목록, 보고서·오류 API |
| 제어·복구 | 호출 횟수·시간·결과 크기 제한, 중복 접수 방지, 재시작 후 상태 정리 |

해커톤 MVP는 하나의 조사 에이전트가 공통 도구를 사용하는 구조다. 도구와 모델의 입출력 형식을 고정하고 실제 조사 결과를 저장한다. 모델 제공자·모델명은 실행 환경이 정해지면 기록한다.

## 3. 제공할 API

| API | 제공할 결과 |
| --- | --- |
| `POST /api/investigations` | 입력을 저장하고 `202`·조사 ID·현재 상태 반환 |
| `GET /api/investigations/{investigationId}` | 상태·도구 실행 요약·근거 목록·리포트·오류 |
| `GET /api/investigations/{investigationId}/evidence/{evidenceId}` | 해당 조사에 속한 근거의 원문·출처 |

요청·응답 DTO와 JSON 예제는 [VOC·Agent 연동 계약](../integration-contract.md)을 따른다. 같은 티켓·요청 키의 중복 접수는 기존 조사에 연결하고, 다른 입력을 같은 키로 보내면 `409`를 반환한다.

조사 상태는 `QUEUED → RUNNING → COMPLETED | NEEDS_INPUT | FAILED`다. 필요한 정보가 없어 조사 대상을 정하지 못하면 추가 입력 항목을 포함한 `NEEDS_INPUT` 결과를 만든다.

## 4. 구현할 조사 도구

| 도구 | 입력 | 반환할 사실 |
| --- | --- | --- |
| `findOrders` | 고객 ID·체크아웃 키·시간 범위 중 확보한 조건 | 주문 후보와 구분에 필요한 요약 |
| `getOrderContext` | 주문 ID | 주문 상품·금액·상태, 결제·환불, 쿠폰 사용 기록 |
| `getCouponContext` | 고객 ID, 선택적 발급 쿠폰 ID | 소유·유효기간·사용 상태·할인 정책 |
| `getInventoryContext` | 상품 ID·시간 범위 | 초기·현재 재고, 변경 이력, 관련 주문·예약 수량 |
| `searchLogs` | 요청·주문·상품·체크아웃 키·시간 범위 중 확보한 조건 | 일치하는 로그와 파일·줄 번호 |
| `searchCode` | 빌드 ID·검색어, 선택적 허용 경로 | 일치하는 실행 소스의 경로·줄 번호 |
| `readCode` | 빌드 ID·허용 파일 경로·줄 범위 | 실제 소스 내용과 조회한 줄 범위 |
| `readBusinessPolicy` | 정책 버전 | 정상 업무 정책과 출처 |

DB·로그·소스의 필드와 위치는 [커머스 인터페이스](../commerce-interface.md)를 따른다. 넓은 검색은 건수·시간 범위를 제한하고 잘린 결과에는 그 사실을 표시한다. 모델에 임의 SQL이나 셸 실행 도구를 주지 않고, 위 조회 기능을 Java 메서드로 구현한다.

## 5. 분석과 리포트 규칙

- 문의에 알려진 원인을 직접 대응시키는 방식으로 답하지 않고 실제 근거를 수집한다.
- 같은 주문·상품·요청·실행 버전의 증거를 연결하고 정상 업무 정책과 비교한다.
- DB에 나타난 결과와 코드에서 추정한 경로를 구분한다. 코드를 읽었다는 사실만으로 실제 실행을 확정하지 않는다.
- 리포트의 모든 `evidenceIds`는 해당 조사에서 수집·저장한 근거를 가리킨다.
- 원인 후보의 근거 수준과 남은 확인 사항을 적고, 필요한 정보가 없으면 입력을 요청한다.
- 해결방안은 해당 건의 운영 조치와 코드·정책의 재발 방지를 각각 제시한다.
- 모델이 반환한 리포트의 필드·상태·근거 참조를 검증한 뒤 저장한다. 검증에 실패하면 제한된 재시도 후 오류로 기록한다.
- 진행 내역은 실제 도구 호출과 결과 요약을 사용한다.

Agent는 커머스 DB를 SELECT로 조회하고 코드·로그를 읽는다. 티켓 처리와 커머스 데이터 변경, 코드 수정 적용은 담당자의 작업으로 남긴다. 평가 정답·시드·시나리오 실행 코드·해커톤 보고서는 조사 검색 범위에서 제외한다.

## 6. 다른 담당자로부터 받을 것

| 제공자 | 필요한 자료 |
| --- | --- |
| 이상효 | 커머스 DDL, SELECT 연결, 예제 데이터·로그, 실행 소스·manifest, 정상 업무 정책 |
| 김아름 | 티켓 ID·버전·요청 키·문의·조사 대상 정보, 추가 정보와 이전 조사 ID |

커머스의 결함 위치와 평가 정답은 테스트 기준으로만 관리한다. 실제 조사 실행에는 문의와 식별자, 정상 정책, 조회 도구를 제공한다.

## 7. 구현 순서와 완료 기준

1. 계약에 맞는 조사 접수·상태·근거 API와 예제 리포트를 먼저 제공한다.
2. 커머스 조회 SQL·로그·소스 도구를 연결하고 모델의 실제 도구 호출을 검증한다.
3. VOC-07에서 데이터·로그·코드를 연결한 원인과 수정 제안을 생성한다.
4. 나머지 6개 시나리오와 정상·정보 부족 사례로 공통 조사 흐름을 검증한다.

완료 조건:

- [ ] 김아름이 같은 계약으로 접수·진행·리포트·근거를 조회할 수 있다.
- [ ] 실제 도구 호출과 모델 응답을 저장하고 원문 근거를 다시 열 수 있다.
- [ ] 서비스 프롬프트가 실제 모델 요청에 적용되고, 접수한 작업이 실행기를 거쳐 검증된 보고서와 종료 상태로 저장·반환된다.
- [ ] 7개 시나리오를 같은 조사 흐름과 도구로 분석한다.
- [ ] 정상적인 쿠폰 거절·주문을 장애로 단정하지 않고 정보 부족을 표시한다.
- [ ] 접수 중복, 도구 실패, 시간 초과, 보고서 형식 오류를 검증했다.
- [ ] 사용한 모델·설정과 분석 시간·실패 내역을 상태 문서와 평가 자료에 기록했다.
