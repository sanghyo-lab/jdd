# 이상효 — 문제가 있는 이커머스 애플리케이션

## 1. 만들 결과

주문·결제·쿠폰·재고·취소 기능을 가진 작은 이커머스를 만든다. [7개 VOC](../voc-scenarios.md)의 문제가 독립적으로 재현돼야 하며, 한재홍의 Agent가 원인을 조사할 수 있도록 업무 데이터·로그·실행 소스를 제공한다.

| 항목 | 담당 범위 |
| --- | --- |
| 실행 앱 | `commerce-app`, 기본 포트 `8080` |
| 업무 로직 | `commerce-core`: 상품·주문·결제·쿠폰·재고·취소 |
| 저장·외부 연동 | `commerce-infra`: JPA·SQL, 마이그레이션, 모의 결제·환불 |
| DB | `commerce` 스키마 |
| 재현 자료 | `fixtures/commerce/VOC-01/`부터 `VOC-07/`까지 |
| 업무 기준·진행 기록 | `docs/business-policy.md`, `docs/status/commerce.md` |

## 2. 구현할 기능

| 기능 | 구현 내용 | 확인할 결과 |
| --- | --- | --- |
| 상품·재고 | 상품 목록·상세, 가격·가용 수량, 변경 이력 | 상품 ID로 주문과 재고 이력을 연결할 수 있음 |
| 주문 | 고객·체크아웃 키·상품 수량·쿠폰으로 생성, 목록·상세 조회 | 금액과 상태, 요청 식별자가 저장됨 |
| 결제 | 카드·간편결제 모의 승인 | 승인 기록과 주문 상태를 각각 조회할 수 있음 |
| 쿠폰 | 보유 쿠폰, 최소 금액, 정액·정률·최대 할인, 사용 기록 | 정책과 실제 계산·거절 결과를 대조할 수 있음 |
| 취소·환불 | 전체 취소, 재고 반환, 모의 환불, 쿠폰 복원 | 주문 취소와 환불 상태를 별도로 확인할 수 있음 |
| 재현·초기화 | 시나리오별 시드, 요청 순서, 기대 관측 결과 | 초기화 후 같은 문제를 다시 만들 수 있음 |

정상 업무 기준은 [업무 정책](../business-policy.md)이다. 아래 결함만 의도적으로 재현하고, 관련 없는 기능은 정상 동작하게 구성한다.

## 3. 반드시 재현할 문제

| ID | 넣을 결함 | Agent가 찾을 수 있어야 하는 흔적 |
| --- | --- | --- |
| VOC-01 | 특정 결제 수단에서 주문 상태 갱신 누락 | 승인된 결제, 결제 대기 주문, 승인 로그, 누락된 상태 전이 |
| VOC-02 | 최소 주문금액과 같은 금액을 제외 | 50,000원 기준·주문, 쿠폰 거절 로그, 잘못된 비교식 |
| VOC-03 | 정률 계산의 정수 나눗셈 | 60,000원·10% 쿠폰의 0원 할인, 계산 로그·코드 |
| VOC-04 | 같은 체크아웃 키의 재시도를 중복 주문으로 처리 | 같은 키의 주문 두 건과 요청 로그 |
| VOC-05 | 일시적인 환불 실패 후 재처리 누락 | 취소 주문, 환불 실패 로그, 환불 완료·재처리 기록의 부재 |
| VOC-06 | 취소 완료 후 쿠폰 사용 상태 해제 누락 | 취소·환불 완료와 유효한 쿠폰의 사용 상태 |
| VOC-07 | 재고 검사와 차감 사이의 경쟁 조건 | 재고 1개를 읽은 두 요청, 주문 2건, 차감 이력·코드 |

VOC-07은 두 요청이 각각 재고를 확인한 뒤 차감하도록 테스트용 동기화 지점을 제공한다. 서로 다른 요청 키와 DB 트랜잭션으로 실행하고, 대기 제한 시간과 해제 동작을 둔다. 초기 재고와 주문·예약 수량을 함께 기록한다. 자세한 재현 조건은 [시나리오 문서](../voc-scenarios.md)를 따른다.

## 4. 다른 담당자에게 제공할 인터페이스

### 김아름에게: 커머스 HTTP API

상품·주문·결제·취소·쿠폰 API를 [커머스 인터페이스](../commerce-interface.md)에 맞춰 제공한다. 김아름은 이를 최소 `/shop` 화면과 `scenario-runner`에서 사용한다. 생성한 주문·상품 ID와 `requestId`를 반환해 VOC 티켓의 조사 대상 정보로 넘길 수 있게 한다.

### 한재홍에게: 읽기 가능한 근거

- `commerce` 스키마 DDL과 SELECT 전용 연결 정보. 접속 비밀 값은 환경 파일로 전달한다.
- 계약에 명시한 테이블·컬럼·상태 값과 초기 데이터.
- 요청·주문·상품·결제 식별자로 연결되는 JSON Lines 로그.
- 로그의 `buildId`와 일치하는 Java·SQL 소스 스냅샷과 manifest.
- 정상 업무 정책 `demo-v1`.

로그 이벤트명, DB 필드, 소스 경로를 변경하면 [공통 계약](../commerce-interface.md)과 `docs/status/commerce.md`에 영향과 변경 커밋을 기록한다. Agent가 업무 데이터를 바꾸지 않고 조회만으로 조사할 수 있어야 한다.

## 5. 재현 자료 전달

각 `fixtures/commerce/VOC-XX/`에는 초기화·시드 SQL, 실행 요청을 설명한 `README.md`, 기대 관측값을 설명한 `expected.md`를 제공한다. SQL은 해당 시나리오의 데모 데이터에 한정한다. 다른 실행과 섞이지 않도록 시나리오 실행은 별도 데모 DB에서 순차 진행하고, VOC-07 내부 요청만 동시에 실행한다.

김아름은 이 자료를 기반으로 `scenario-runner`에서 초기화·요청·검증을 자동화한다. 기대 정답·시드·테스트 동기화 코드는 Agent에게 제공하는 소스 검색 범위에서 제외한다.

## 6. 구현 순서와 완료 기준

1. 커머스 마이그레이션, 상품·재고·주문과 추적 식별자를 구현한다.
2. VOC-07의 재현 데이터·동시 요청 조건·로그·소스를 제공해 첫 통합을 연다.
3. 결제·쿠폰·취소·환불과 나머지 6개 시나리오를 구현한다.
4. 정상 대조 사례와 독립 재실행을 검증하고 실제 결과를 기록한다.

완료 조건:

- [ ] 김아름이 계약에 맞는 API로 주문·결제·취소를 실행할 수 있다.
- [ ] 한재홍이 같은 상품·주문·요청을 DB·로그·소스에서 연결할 수 있다.
- [ ] 7개 결함이 독립적으로 재현되고 정상 대조 사례는 정상 동작한다.
- [ ] 재고 동시 요청의 성공 주문 수와 재고 이력이 실제 DB에서 확인된다.
- [ ] 초기화 방법, 실행 환경, 실제 검증 결과를 상태 문서에 기록했다.

문제 원인의 분석·리포트 생성은 한재홍, 티켓·화면·전체 흐름 검증은 김아름이 담당한다. 결함을 수정한 비교 버전은 기본 시연이 끝난 뒤 추가 범위로 다룬다.
