# 이상효 — 개발리더와 최종 검증 책임

이상효는 commerce 구현과 개발리더 역할을 겸한다. 인원이나 병렬 세션을 추가하지 않고 같은 PC의
commerce goal에서 [리더 검증 단계](../goals/lead.md)를 이어 수행한다. 사용자는 전체 코드 검사와
검증을 통해 다른 담당 영역도 직접 수정·보완하고 최종 완료를 판단할 권한을 부여했다.

## 권한과 책임

- commerce·agent·voc·web·scenario-runner·인프라·테스트·계약을 모두 읽고 검증하며 필요한 수정을 직접 수행한다.
- 세 담당자의 DONE은 최종 검토의 시작 조건이다. 자기 commerce 구현도 동일한 기준으로 다시 검사한다.
- 다른 담당자의 결과표만 인용하거나 기존 성공 로그를 재사용해 최종 승인하지 않는다.
  최신 main의 실제 코드와 DB·로그·보고서·화면을 직접 확인하고 자신의 PC에서 전체 검증을 새로 실행한다.
- 발견한 문제는 LEAD-001 같은 ID로 대상 역할, 재현 방법, 예상·실제 결과, 수정과 재검증 근거를 기록한다.
- 직접 수정할 때 다른 담당자의 진행 상태를 확인하고 변경 경로·이유·계약 영향을 [리더 상태](../status/lead.md)에 공유한다.
  담당자에게 수정을 요청할 수도 있으며, 해결 완료는 리더가 다시 확인한다. 사람의 중간 승인을 기다리는 절차는 추가하지 않는다.
- 역할별 완료 선언은 각각의 담당자가 유지한다. 리더가 다른 사람의 DONE을 대신 작성하지 않는다.
  리더 수정으로 코드가 바뀌면 세 담당자는 최신 코드에서 완료 기록을 갱신하고 리더도 재검증한다.

## 코드 검사 범위

| 영역 ID | 반드시 살펴볼 대상 |
| --- | --- |
| commerce | 업무 정책, 금액·수량·상태 전이, 트랜잭션·동시성, 마이그레이션, 의도한 7개 결함과 정상 대조 테스트 |
| agent | 실제 모델과 도구 실행, 근거 저장·참조, SELECT 전용 접근, 평가 정답 노출 방지, 오류·시간 초과·복구 |
| voc | 입력 스냅샷·버전, 요청 키·재전송·재조사, 상태 구분, Agent 연결·저장·복구 |
| web | 실제 API 연결, 티켓 입력·조회·분석 요청·결과·근거 열람, 오류·대기·정보 부족 표시 |
| scenarios | 초기화와 데이터 격리, 실제 결과 단언, 정상·예외·복구, 반복 재현, 테스트 누락·무조건 성공·skip 여부 |
| runtime | 빌드·환경 설정·Compose·DB 권한·소스와 로그 볼륨·CI·실행 스크립트 |
| contracts | 제공자와 소비자의 API·DDL·로그 일치, 정책과 시연 목적, 완료 기준·실행 문서의 정확성 |

영역마다 실제 검토한 추적 파일 경로와 판단 이유를 남긴다. 핵심 구현뿐 아니라 연결된 테스트·설정·마이그레이션도 읽는다.
시연용 결함은 재현 대상으로 유지하고 그 밖의 오류를 수정한다. 테스트 통과만으로 코드 검사를 생략하지 않는다.

## 검증 기록

[lead-review.json](../status/lead-review.json)은 미검토 상태의 양식이다. 아래 값을 실제 검토 후 작성해 커밋·publish한다.

- reviewedCommit: 검토한 전체 커밋 SHA. `git rev-parse HEAD`로 확인한다.
- contentSha256: `./scripts/dev team-status`에 표시되는 현재 저장소 내용 해시. 최신 원격과 로컬 코드가 같은지 먼저 확인한다.
- areas: 위 7개 영역마다 id, 실제 추적 파일의 paths 배열, 검토 내용과 판단을 설명하는 summary.
- checks: 아래 7개 검사마다 id, status=PASSED, 실행 명령·관측 결과·근거 위치를 설명하는 evidence.
- reproductions: VOC-01~07 각각 id, runs, passed, 실제 실행 근거인 evidence. 01~06은 3회 이상, 07은 20회 이상이며 모든 실행이 통과해야 한다.
- findings: 발견한 문제의 id, owner(commerce/agent/voc), description, status, resolution, verification.
  미해결은 OPEN, 수정 후 리더가 검증을 끝낸 것만 VERIFIED다. 문제가 없으면 빈 배열을 유지한다.

| 검사 ID | 실제 확인할 결과 |
| --- | --- |
| requirements | 역할별 필수 요구사항에 미구현·임시 응답·미처리 연동 요청이 없음 |
| normal-and-errors | 정상 대조·경계값·잘못된 입력·정보 부족 처리가 정책과 계약에 맞음 |
| evidence-integrity | DB·로그·실행 소스·리포트 근거가 실제 관측과 일치하며 정답 자료가 조사 입력에 포함되지 않음 |
| data-isolation | 시나리오 초기화·재실행이 격리되고 다른 실행의 합성 데이터를 손상하지 않음 |
| retries-and-recovery | 재전송·중복·재조사·통신 실패·재시작 시 상태와 저장 결과가 계약에 맞음 |
| ui-flow | 실제 화면에서 티켓→분석→보고서→근거 열람과 오류·대기 표시를 확인 |
| repeatability | 모든 반복 재현의 실제 결과를 보관하고 원인 미해결인 간헐적 실패가 없음 |

실제 검토와 실행 없이 양식을 PASSED로 채우지 않는다. 원본 비밀 값·개인정보·프롬프트·DB 행은 Git에 올리지 않고
합성 데이터의 식별자와 검증 요약을 기록한다. 기본 양식에는 성공 판정이나 승인 기록이 없다.

## 최종 승인과 철회

```bash
./scripts/dev roles-check
./scripts/dev lead-approve
git add -- docs/status/lead.json
git commit -m "chore(lead): approve independently verified project"
./scripts/dev publish
./scripts/dev team-check
```

roles-check는 세 담당자의 유효한 DONE만 확인한다. 프로젝트 완료를 뜻하지 않는다.
lead-approve는 `.jdd-role`이 commerce인 이상효의 clone에서, 공유된 검토 기록을 검사한 뒤 verify-mvp를 새로 실행한다.
검증 중 main이 변경되거나 검토 누락·미해결 지적·실패가 있으면 승인을 작성하지 않는다.
승인은 코드 내용, 검토 기록, 세 담당자의 완료 기록 각각에 묶인다. 이 중 하나라도 바뀌면 최종 완료에 사용할 수 없다.

새 문제를 발견하면 `./scripts/dev lead-reopen`으로 승인을 철회하고 리더 상태·검토 기록과 함께 공유한다.
수정·회귀 검증·담당자 완료 갱신·리더 재검증을 거친 뒤 다시 승인한다.
team-check가 성공하고 [공통 품질 기준](../team-completion.md)까지 충족해야 모든 goal을 완료한다.

이 승인에는 사람이 버튼을 누르는 추가 절차가 없다. 이상효에게 위임받은 개발 에이전트가 실제 검사 후 작성한다.
로컬 역할 파일과 JSON은 신원 인증 장치가 아니며, 도구의 형식 검사가 코드의 무결함을 증명하지도 않는다.
코드 검토와 실제 동작 검증을 수행하고 사실대로 기록할 책임은 개발리더에게 있다.
