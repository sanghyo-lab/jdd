# 김아름 — VOC 티켓 관리와 AI Agent 연동

## 1. 만들 결과

개발팀이 문의를 티켓으로 등록하고, 분석을 요청한 뒤 원인·리포트·해결방안과 근거를 확인하는 내부 도구를 만든다. 티켓 업무 흐름과 Agent 호출을 연결하고, 한재홍이 생성한 구조화된 리포트를 화면에 표시한다.

| 항목 | 담당 범위 |
| --- | --- |
| 실행 앱 | `voc-app`, 기본 포트 `8082` |
| 업무 로직 | `voc-core`: 티켓·담당자·업무 상태·분석 요청 |
| 저장·연동 | `voc-infra`: `voc` 스키마, Agent HTTP 클라이언트 |
| 프론트 | `web`: Next.js 티켓·분석·근거 화면, 최소 `/shop` |
| 전체 흐름 검증 | `scenario-runner`, 시나리오 실행 결과 취합 |
| 진행 기록 | `docs/status/voc.md` |

## 2. 구현할 기능

| 기능 | 구현 내용 |
| --- | --- |
| 티켓 등록·조회 | 제목, 문의, 주문·상품·시각 등 조사 대상 정보, 생성 시각 |
| 티켓 관리 | 목록·상세·내용 수정, 담당자 지정, 상태 필터, `OPEN`·`IN_PROGRESS`·`RESOLVED` |
| 분석 요청 | 현재 티켓 입력의 스냅샷과 요청 키 저장, Agent로 비동기 전달 |
| 진행 상태 | 접수 전달 상태와 AI 조사 상태, 실제 도구 실행 내역, 마지막 확인 시각 |
| 분석 리포트 | 요약·사실·원인 후보·해당 건 조치·재발 방지·부족한 정보 표시 |
| 근거 열람 | 리포트의 `evidenceId`를 선택해 DB·로그·코드·정책 출처와 원문 확인 |
| 재조사 | 추가 정보로 새 분석을 시작하고 이전 결과와 연결 |
| 오류 처리 | Agent 연결 실패, 접수 응답 유실, 조회 실패, 분석 실패를 구분해 표시 |

티켓 목록·상세와 상태 관리를 MVP로 둔다. 댓글·첨부파일·실시간 공동 편집·세밀한 권한 관리·PDF 출력은 후속 범위다. 공통 사용자 접근 제어와 서버 간 인증은 [프론트 설계](../frontend-deployment.md)를 따른다.

## 3. 제공할 인터페이스

`web`에 [공통 연동 계약](../integration-contract.md)의 티켓·분석 API를 제공한다. 티켓별 분석 이력과 각 분석의 입력 스냅샷을 저장하고, Agent의 조사 ID를 연결한다.

- `ticketId`: VOC 서버가 발급한다.
- `ticketVersion`: 티켓 수정마다 증가하는 버전이다. 수정 시 `expectedVersion`, 분석 요청 시 `ticketVersion`으로 화면에서 확인한 버전을 전달한다.
- `analysisRequestId`: VOC 서버가 분석 요청마다 발급한다.
- `requestKey`: 새 분석을 의도할 때 프론트가 생성하고 통신 재시도에는 재사용한다.
- `investigationId`: Agent가 발급하며 VOC 서버가 응답을 받아 연결한다.
- 보고서 원본: Agent가 관리한다. VOC가 복사해 표시할 때에는 원본 조사 ID·갱신 시각을 함께 보존한다.

분석 요청은 저장 직후 `202`로 응답한다. VOC의 서버 작업이 접수 전달과 상태 갱신을 맡아 브라우저가 닫혀도 계속 진행한다. Agent API 호출에 LLM API 키를 사용하지 않으며, 필요하면 별도 서버 간 인증 값을 사용한다.

## 4. 다른 담당자로부터 받을 것

| 제공자 | 필요한 결과 | 개발 중 사용할 대체 자료 |
| --- | --- | --- |
| 한재홍 | 조사 POST·GET·근거 GET, 상태·리포트 DTO, 실제 오류 응답 | 공통 계약의 JSON 예제로 만든 명시적인 개발용 응답 |
| 이상효 | 커머스 API, 시드·초기화 방법, 7개 재현 조건 | 커머스 계약의 예제 요청·응답 |
| 두 담당자 | 앱 실행 방법, 포트·환경 변수, 상태 확인·검증 명령 | 초기 공통 실행 틀의 각 앱 설정 |

구현 완료를 기다리는 동안 티켓 저장과 계약에 맞는 화면을 만들 수 있다. 첫날에 개발용 응답을 실제 Agent·커머스 연결로 교체해 전체 흐름을 확인한다.

## 5. 반드시 지킬 상태·리포트 규칙

1. **티켓 상태와 AI 상태를 별도로 다룬다.** AI의 `COMPLETED`만으로 티켓을 `RESOLVED`로 바꾸지 않는다.
2. **보고서의 판단과 근거를 그대로 연결한다.** UI가 별도 원인을 추정하거나 없는 근거를 생성하지 않는다.
3. **통신 오류를 분석 실패로 바꾸지 않는다.** Agent 조회 실패에는 마지막 확인 상태·시각과 재조회 오류를 표시한다.
4. **재전송과 재조사를 구분한다.** 같은 요청의 재전송은 같은 키, 보완된 입력의 재조사는 새 키를 쓴다.
5. **이력을 유지한다.** 티켓 내용을 수정해도 기존 분석의 버전·입력·보고서를 덮어쓰지 않는다. 버전 충돌 시 최신 티켓을 확인하게 한다.
6. **티켓에 연결된 근거만 제공한다.** 다른 티켓의 조사·근거 ID로 내용을 조회할 수 없어야 한다.

`NEEDS_INPUT`에서는 `report.missingInformation`을 이용해 추가 입력을 안내한다. `FAILED`에서는 오류 코드와 재시도 가능 여부를 표시한다. 해결방안은 개발자가 검토할 제안으로 표시한다.

## 6. 구현 순서와 완료 기준

1. VOC 스키마와 티켓 생성·목록·상세·수정 API를 구현한다.
2. 예제 응답으로 분석 상태·리포트·근거 화면을 구현한다.
3. Agent 비동기 접수·조회·재전송과 티켓별 분석 이력을 연결한다.
4. 이상효의 재현 자료로 VOC-07 한 건을 실제 리포트까지 연결한다.
5. 7개 시나리오·정상·정보 부족·통신 실패를 검증하고 화면·실측값을 취합한다.

완료 조건:

- [ ] 티켓을 등록·배정·진행·해결 처리할 수 있다.
- [ ] 실제 Agent 분석이 티켓의 보고서·해결방안으로 표시된다.
- [ ] 코드 줄·로그 위치·DB 식별자를 가진 근거 원문을 열 수 있다.
- [ ] 같은 요청의 재전송과 추가 정보를 넣은 재조사를 각각 검증했다.
- [ ] 새로고침·브라우저 종료 후에도 저장된 티켓과 분석 결과를 조회할 수 있다.
- [ ] 일시적인 Agent 조회 실패와 Agent 자체 실패를 구분해 표시한다.
- [ ] 실제 실행한 시나리오와 측정 결과를 [해커톤 보고서](../hackathon-report.md)에 반영했다.
