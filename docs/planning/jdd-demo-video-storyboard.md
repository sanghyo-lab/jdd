# JDD 시연 영상 — 7개 시나리오·정답 검수·내레이션 초안

[제작 실행 프롬프트](../prompts/produce-jdd-demo-video.md)의 부속 제작 자료다. 정답은 제작자 검수용이며 서비스 AI에 전달하지 않는다. 아래 대본은 실제 조사 보고서와 근거를 확인한 뒤 확정하는 **조건부 초안**이다. 기대한 원인이 실제 보고서에 없거나 인용이 틀리면 대본으로 결과를 보충하지 않는다.

검토한 기준은 2026-09-22 `86d6f6a`의 시나리오·정상 정책·각 fixture expected와 실제 web/runner 코드다. 그 시점의 일곱 조사 전체 통과를 뜻하지 않는다. 이후 변경과 실제 결과를 촬영 직전에 다시 확인한다.

## 모든 case에 적용할 촬영 문법

최종 40~50초 정도를 시작 목표로 잡되 실제 녹화·음성 길이로 확정한다. 아래 비율은 고정 timecode가 아니라 화면과 발화의 의미 구분이다.

| 구간 | 화면 | 설명 내용 | 목표 비중 |
| --- | --- | --- | --- |
| A | `/shop`의 실제 증상 또는 사전 재현 상태 | 고객이 겪은 문제·핵심 숫자 | 약 15% |
| B | `/tickets`의 자연어 문의와 실제 context, 분석 이력 | 무엇을 입력했고 어떤 조사를 보는지 | 약 15% |
| C | 보고서의 확인 사실과 DATA·LOG 원문 | 실제로 관측된 값·이벤트 | 약 30% |
| D | 같은 사건·build의 CODE·POLICY 근거 | 정상 규칙과 실행 경로의 차이 | 약 25% |
| E | 해당 건의 조치·재발 방지 | 사람에게 제안한 조치, 자동 적용하지 않음 | 약 15% |

각 구간을 보면서 다음의 짧은 문장들을 배치한다. 실제 근거 원문을 읽을 시간을 원본 녹화에 확보한다. 순서만 맞고 음성이 다른 화면을 가리키면 다시 편집한다. 긴 모델 대기는 원본을 보존하고 생략 표시와 함께 편집할 수 있지만 결과를 미리 준비된 정답으로 대체하지 않는다.

공통 입력 화면은 `문의 작업실` → 제목/문의 → `주문·상품 등 참고 정보` → `문의 등록`이다. 고객·주문·상품·요청 번호, 체크아웃 키, 발생 시각은 실제 값만 쓴다. 쿠폰 번호는 현재 전용 context 필드가 없으므로 필요하면 문의 본문에 실제 번호를 적는다. `/shop`의 링크가 식별자를 자동 복사한다고 가정하지 않는다.

새 실제 조사는 상세의 `분석 요청`을 사용한다. 이미 검수한 실제 저장 보고서를 보여줄 때는 분석 이력을 선택하고 “실제 조사 결과 재생”을 표시한다. `현재 버전으로 새 분석 요청`은 단순 새로고침이 아니므로 촬영 재시도에 쓰지 않는다. 상태 재조회와 근거 GET으로는 새 보고서를 만들지 않는다.

새 case를 시작할 때 `/shop`에 `저장된 주문 요청`이 있으면 `새 주문 입력`으로 이전 요청을 해제하고 새 합성 고객·상품·쿠폰을 확인한다. 거절된 요청도 sessionStorage에 남아 입력을 잠그므로 case 전환마다 확인한다. VOC-04의 같은 요청 재전송 사이에서는 해제하지 않는다.

## VOC-01 — 결제 상태 불일치

근거: [재현 준비](../../fixtures/commerce/VOC-01/README.md), [정답 검수](../../fixtures/commerce/VOC-01/expected.md), [결제 처리 코드](../../commerce-core/src/main/java/com/jdd/commerce/payment/application/PaymentService.java).

**고객 문의:** “간편결제로 결제가 승인됐는데 주문 화면에는 계속 결제 대기라고 나옵니다. 같은 금액을 다시 결제해야 하는지 확인해 주세요.” 실제 주문·고객 번호·발생 시각을 전달한다.

**화면 순서:** 새 합성 prefix의 상품을 `/shop`에서 `상품 번호로 조회` → 수량 1·쿠폰 없음으로 `주문 생성` → `간편결제`로 `결제 요청` → 실제 결제 응답 APPROVED와 주문 결제 대기를 보여준다. 이어 문의와 보고서, 같은 주문의 DATA/승인 LOG, CARD 분기 CODE, 정상 POLICY, 사람 조치를 연다. 저장 주문을 GET으로 불러왔을 뿐이라면 과거 결제 응답 배너가 복원된다고 가정하지 않고 보고서 근거에서 승인 기록을 보여준다.

**제작자 정답:** `payments`는 APPROVED/EASY_PAY, 같은 주문은 PAYMENT_PENDING. 같은 주문·결제의 PAYMENT_APPROVED 로그가 있으며 실행 소스는 CARD일 때만 주문을 PAID로 전이한다. 카드 대조는 정상이다. 모의 제공자 승인과 실제 외부 결제사 원장 조회를 혼동하지 않는다.

**발화 초안:**

> 간편결제는 승인됐지만 주문은 결제 대기로 남아 있습니다. 문의에는 증상과 조사에 필요한 식별자를 입력했습니다. 조사 결과에서 같은 주문의 승인 기록과 로그를 열고, 실행한 코드까지 연결해 확인합니다. 카드 결제에만 주문 상태를 바꾸는 분기가 있어 두 상태가 어긋났습니다. 제안은 재결제가 아니라 승인 내역을 확인한 뒤 주문 상태를 복구하고, 결제 수단에 관계없이 성공 처리를 맞추는 것입니다. 실제 데이터 변경은 사람이 검토합니다.

**cue:** “승인”은 승인 DATA/응답, “코드”는 해당 상태 전이 분기, “재결제가 아니라”는 검수된 사람 조치 화면. 모든 결제가 실패했다거나 이미 주문을 자동 복구했다고 말하지 않는다.

## VOC-02 — 쿠폰 적용 거절

근거: [재현 준비](../../fixtures/commerce/VOC-02/README.md), [정답 검수](../../fixtures/commerce/VOC-02/expected.md), [runner 준비](../../scenario-runner/scripts/prepare.py), [쿠폰 코드](../../commerce-core/src/main/java/com/jdd/commerce/coupon/application/CouponService.java).

**고객 문의:** “5만 원 이상 주문에 쓸 수 있는 쿠폰인데, 5만 원짜리 상품 한 개를 주문하면 적용할 수 없다고 나옵니다. 아직 쓰지 않은 제 쿠폰입니다.” 실제 고객·상품·체크아웃 키·발생 시각, 필요하면 실제 쿠폰 번호를 넣는다. 주문 생성 전 실패이므로 주문번호를 만들어 넣지 않는다.

**화면 순서:** 새 prefix에서 50,000원 상품 조회 → `고객 쿠폰 조회` → 유효한 AVAILABLE 정액 쿠폰 선택 → `주문 생성` → 실제 최소금액 거절 확인 → 문의 → 소유·기간·상태와 금액 DATA → COUPON_REJECTED LOG → 비교식 CODE와 최소금액 POLICY → 경계 검증 제안.

**준비 주의:** 일반 `reproduce_commerce.py --scenario VOC-02`는 같은 쿠폰으로 50,001원 대조도 성공시켜 최종 USED가 된다. 이를 미사용 쿠폰의 촬영 사건으로 재사용하지 않는다. runner 준비 코드처럼 50,000원 실패만 만든 새 데이터에서 AVAILABLE·주문/사용이력 없음·예약 없음이 유지되는지 확인한다. 49,999원·50,001원 대조는 별도 prefix/쿠폰에서 수행한다.

**제작자 정답:** 상품 합계와 최소금액은 모두 50,000원. 소유·기간·사용 상태는 정상이며 거절 로그 reasonCode는 MIN_ORDER_AMOUNT. 정책은 같은 금액을 허용하지만 구현은 `subtotal <= minOrderAmount`를 거절한다. 49,999원 거절은 정상이고 50,000원/50,001원은 허용해야 한다. 원인 항목에 이 사건 DATA·LOG·CODE·POLICY의 직접 근거가 있는지 특히 확인한다.

**발화 초안:**

> 이 쿠폰은 5만 원 이상이면 사용할 수 있지만, 정확히 5만 원인 주문이 거절됐습니다. 먼저 고객 소유인지, 유효기간 안인지, 아직 사용하지 않았는지 확인합니다. 이어 거절 로그와 실행 코드를 열면 기준 금액과 같은 경우까지 제외하는 비교식이 보입니다. 정상 정책과 비교해 경계값 오류를 설명하고, 4만 9,999원은 거절, 5만 원과 5만 1원은 허용하는 검증을 제안합니다. 주문이 생성되지 않은 사실도 별도 근거로 확인합니다.

**cue:** 세 금액의 허용/거절 설명은 해당 POLICY/검증 제안이 보이는 구간에 둔다. 주문 없음은 별도 DATA 근거에서 확인한다. 없는 주문의 취소·환불을 제안하거나 인용 실패 보고서를 성공으로 설명하지 않는다.

## VOC-03 — 할인금액 0원

근거: [재현 준비](../../fixtures/commerce/VOC-03/README.md), [정답 검수](../../fixtures/commerce/VOC-03/expected.md), [쿠폰 코드](../../commerce-core/src/main/java/com/jdd/commerce/coupon/application/CouponService.java).

**고객 문의:** “6만 원짜리 상품에 10% 쿠폰을 적용했는데 할인은 0원이고 결제 금액도 6만 원으로 나옵니다. 쿠폰은 사용한 것으로 표시됩니다.” 실제 주문·고객·상품 번호를 전달한다.

**화면 순서:** 60,000원 상품 → 고객의 PERCENT 10% 쿠폰 → 주문 생성 → 합계 60,000원/할인 0원/결제할 금액 60,000원·쿠폰 USED → 보고서 → 쿠폰/주문/사용이력 DATA → DISCOUNT_CALCULATED LOG → 할인 계산 CODE → 정상 6,000원 할인 POLICY·수정 제안. 실제 결제를 추가할 필요는 없다.

**제작자 정답:** 10%·최대 할인 10,000원, 실제 할인 0원·사용이력 ACTIVE/할인 0. 할인율을 정수로 100으로 먼저 나눠 0이 된 뒤 금액에 곱한다. 정상 할인은 6,000원이다. 60,000원은 VOC-02 경계와 원인을 분리한다.

**발화 초안:**

> 6만 원 주문에 10% 쿠폰이 적용됐지만 할인액은 0원입니다. 에이전트는 주문 금액만 보는 것이 아니라 쿠폰 정책과 사용 기록, 실제 할인 계산 로그를 함께 확인합니다. 실행 코드에서는 할인율을 정수로 100으로 먼저 나누면서 값이 0이 됩니다. 정책에 맞는 할인액은 6천 원입니다. 조치는 해당 주문의 결제 여부와 금액을 확인한 뒤 검토하고, 재발 방지에는 소수 계산과 원 단위 처리, 할인 상한 검증을 제안합니다.

**cue:** 0원은 실제 주문/로그, 6천 원은 정상 정책과 검수된 제안 구간에서 말한다. 기대 할인 6,000원을 실제 할인 결과처럼 덧씌우지 않는다. 결제하지 않은 주문을 이미 과다 청구·환불 완료로 설명하지 않는다.

## VOC-04 — 중복 주문

근거: [재현 준비](../../fixtures/commerce/VOC-04/README.md), [정답 검수](../../fixtures/commerce/VOC-04/expected.md), [주문 코드](../../commerce-core/src/main/java/com/jdd/commerce/order/application/OrderService.java), [실제 shop 화면](../../web/components/shop.tsx).

**고객 문의:** “주문 화면에서 응답이 늦어 같은 주문을 다시 보냈더니 주문번호가 두 개 생겼습니다. 같은 상품을 두 번 주문하려던 것은 아닙니다.” 실제 고객·체크아웃 키·발생 시각을 전달하고 필요하면 실제 주문번호 두 개를 본문에 넣는다.

**화면 순서:** 충분한 재고·쿠폰 없는 상품으로 주문 생성 → `새 주문 입력`을 누르지 않고 `같은 주문 요청 다시 전송` → 두 주문 목록 → 각 상세의 같은 체크아웃 키와 다른 주문번호 → 보고서 DATA → ORDER_CREATED LOG 두 건 → 생성 CODE/유일성 검토 → 조치 제안. 실제 응답 지연을 재현하지 않았다면 정상 응답 장면을 네트워크 장애처럼 편집하지 않고 고객 문의의 배경으로만 설명한다.

사람의 반복 승인 절차가 아니라 제작 담당자가 실제 근거로 채우는 점검표다. 준비 단계에서는 전부 미확정이다. 일곱 case 각각 아래 값을 파일로 남긴다.

| 사건 | case·fixture prefix·주문/상품·발생 시각·정상 대조의 분리 여부 |
| 버전 | Git commit·실행 buildId·정책/프롬프트 버전 |
