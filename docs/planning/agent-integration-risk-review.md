# commerce goal에 따른 Agent 누락·영향 분석

검토일: 2026-09-21. 구현·배포·goal 실행이 아닌 설계 검토다.
사용자가 전달한 이상효의 goal은 commerce의 협업 조건으로 분석한다. 한재홍의 역할을 commerce로 변경하지 않는다.
초기 검토 기준 커밋은 `be530f4`이며 검토 도중 다른 세션이 반영한 `08b3ba4`의 프롬프트·goal 보완도 확인했다.
해당 세션의 기존 변경은 유지하고 비용·통합 영향에 대한 추가 검토를 반영한다.
후속 원격 `c9ecf7a`까지 확인해 데모 전용 키 정책과 `e6280e5`의 개발리더 최종 검토를 추가 반영했다.
세 역할과 리더 완료 기록은 IN_PROGRESS다. 아래 잠재 상황은 실제 재현한 결함과 구분한다.
LLM 실행은 [데모 키·비용 규칙](demo-llm-policy.md)을 따른다. 제공된 OpenAI 키는 개발·CI·자동 반복 평가에 사용하지 않으며,
승인된 데모 범위에서만 실제 모델을 검증한다. $30 초과 예상 시 별도 처리하고 미검증을 DONE으로 바꾸지 않는다.

## 1. 결론과 우선순위

현재 [구현 프롬프트](../prompts/implement-voc-investigation-agent.md)는 API·도구·보고서 기본 범위를 갖춘 상태다.
첫 구현 전에 **재현 데이터의 수명, 증거의 관측 시점, VOC의 실패·재조사 동작, 비용 제어, 팀 완료 절차**를 더 명확히 해야 한다.

| 우선순위 | 한재홍에게 필요한 보완 | 다른 담당자의 참여 |

## 3. 커머스 근거와 재현의 위험·우회 방법

아래 우회 방법은 기존 계약을 유지하는 방법을 우선한다. 계약 변경 제안은 상대 구현과 맞춘 뒤 적용한다.

| ID / 상황 | 영향·누락 | 예방 또는 우회 | 담당·검증 |
| --- | --- | --- | --- |
| C01 조사 중 시드 초기화 | 같은 ID가 새 데이터로 재생성되어 이전 로그·새 DB를 혼합 | runner가 재현→조사 종료→근거 저장 확인 후 초기화. 실행마다 식별자 분리. 조사 자체가 초기화하지 않음 | 이상효·김아름: 순차 실행. Agent: 저장된 근거가 초기화 후에도 유지 |
| C02 publish가 세 앱 재기동 | 조사 중단, 로그 디렉터리·buildId 변경, 시연 끊김 | 통합 시연·평가 구간에는 publish를 겹치지 않게 조율. 재시작 시 남은 RUNNING은 FAILED와 오류 코드 INTERRUPTED로 기록, 기존 증거 유지 | 세 담당자: 재시작 복구·늦은 모델 응답 무시 |
| C03 DB commit과 로그 기록 시차 | DB 성공을 본 시점에 로그가 아직 없어 잘못된 결론 | 사건 완료 뒤 짧고 제한된 로그 재조회. 미기록과 실패를 구분. 로그 부재만으로 실행 누락 확정 금지 | 이상효: 커밋 후 로그. Agent: 시간 범위·관측 시각·검색 범위 기록 |
| C04 JSONL 기록 중 읽기·rotation | 마지막 반 줄을 파싱 실패로 처리하거나 줄 번호가 달라짐 | 완성된 줄까지만 읽고 미완성 끝부분은 재조회. 원문·경로·줄 범위를 저장하고 이후 파일에 재의존하지 않음 | 이상효·Agent: append·rotation·잘림 테스트 |
| C05 정책 파일은 단일 경로 | 예전 buildId에 새 정책을 적용 | demo-v1 내용 고정. 변경하면 새 버전·해시로 제공. 조회 시 정책 원문 보존 | 이상효: 버전별 정책. Agent: manifest 정책과 실제 파일 불일치 검출 |
| C06 SQL 조회 시점 불일치 | 주문·재고·이력을 다른 시점에 읽어 가짜 불일치 생성 | 관련 조회를 짧은 read-only snapshot/transaction으로 묶는 방안 검토. 모델 호출 동안 트랜잭션 유지 금지 | Agent: 일관성·쿼리 timeout. 이상효: 동시 쓰기 대조 |
| C07 조회 제한으로 일부 이력 누락 | 앞 100개만 합산해 재고 불일치를 단정 | 서버 SQL로 같은 필터의 정확한 count/sum과 범위를 계산하고 제한된 원문 별도 제공. 전체 집계와 부분 목록을 구분 | Agent: 대량 이력·잘림 검증. 근거 출처의 테이블/레코드 의미 유지 |
| C08 SELECT 기본 권한의 소유자 차이 | bootstrap는 읽히지만 다른 계정이 만든 새 테이블은 조회 실패 | 실제 migration 소유자와 필요한 모든 테이블 SELECT 확인. 관리 계정으로 우회하지 않고 제공자가 권한 수정 | 이상효: DDL·grant, Agent: 표별 조회 검사 |
| C09 시연 결함의 오수정 | Agent 제안이 적용되어 재현·정상 대조가 달라짐 | 운영 조치와 코드 수정은 제안으로만 반환. 수정 비교는 별도 명시된 시연·평가 범위 | 세 담당자: 결함 재현 유지·조치 미적용 확인 |
| C10 평가 정답의 간접 노출 | 허용 소스의 주석·클래스명·설정이 정답을 알려줌 | fixtures 제외뿐 아니라 소스의 정답 설명·시나리오별 힌트도 검토. 실제 업무 코드 증거는 유지 | 이상효·Agent: 모델 입력 목록과 소스 스냅샷 검토 |
| C11 로컬 통합만 성공하고 외부 연결 미확인 | ngrok가 잘못된 포트에 연결되거나 web의 호스트 주소와 Compose 내부 주소가 혼용됨 | 로컬 web 하나만 ngrok에 연결하고 web은 호스트 VOC·commerce 포트, VOC는 Compose 내부 Agent 주소 사용. 터널 재연결·접근 제어·조사 지속을 확인하고 외부 미검증은 별도 기록 | 김아름·Agent: ngrok URL에서 티켓→실제 조사→근거 열람 확인 |
| C12 SELECT·로그 검색의 자원 소모 | 읽기 전용이어도 전체 검색·동시 조회가 업무 DB·디스크를 압박 | 식별자·시간 범위 제한, 쿼리 timeout·조회 동시성·응답 크기 제한. 필요한 인덱스는 이상효에게 요청. 저장 실패는 근거 없는 성공으로 바꾸지 않음 | Agent·이상효: 큰 이력과 느린 조회에서도 commerce 정상 흐름 확인 |
| C13 새 조사·재시작으로 비용 한도 초기화 | 요청마다 $30을 새로 허용하거나 세 PC가 각각 같은 예산 사용 | 영속 장부에 확정·미확정·예약 비용을 합산. 새 키·모델 전환도 같은 누적 한도 적용. 공유 장부 또는 총액 내 PC별 배분 | Agent·김아름: 동시 예약·재시작·새 키로 우회 불가를 모의 검증 |

현재 DB 권한 초기화는 `jdd_commerce`가 만드는 테이블에 기본 SELECT 권한을 부여한다.
C08은 [초기화 SQL](../../infra/postgres/01-roles.sql)에서 추론한 마이그레이션 계정 변경 시의 위험이며, 현재 발생 확인은 아니다.
C11의 연결 구조와 배포 완료 기준은 [프론트 배포 설계](../frontend-deployment.md)를 따른다.

### 시나리오별 놓치기 쉬운 조사 조건

| 시나리오 | Agent가 빠뜨리기 쉬운 부분 | 대응 |
| --- | --- | --- |

| VOC-04 | 고객·상품이 같다는 이유로 다른 체크아웃 키의 정상 주문까지 중복 판정 | 같은 checkoutKey의 서로 다른 주문인지 확인. Agent 자체 접수 키와 혼용 금지 |
| VOC-05 | refunds 행 부재·로그 미검색을 환불 미실행의 확정 증거로 사용 | 결제·취소·외부 응답·로그 조회 범위를 대조하고 미확인 범위를 limitations에 기록 |
| VOC-06 | 현재 시각의 만료 여부로 사고 당시 복원 정책을 판단 | 취소·발생 시각과 validFrom/validUntil을 대조. 만료 쿠폰은 정상 사용 거절 |
| VOC-07 | 음수 재고나 INVENTORY_READ만으로 초과 판매 확정 | 초기·입고·예약·반환·확정 주문 수량과 서로 다른 요청을 같은 실행 범위로 대조 |

VOC-02 입력 계약에는 customerCouponId가 없다. 우선 허용된 requestId·checkoutKey·customerId·occurredAt으로 조회하고,
쿠폰 후보를 구분할 수 없으면 허용 필드 또는 message로 추가 정보를 요청한다.
customerCouponId를 context에 추가하려면 김아름의 타입·폼·스냅샷·검증과 Agent를 함께 맞추는 추가 계약으로 다룬다.
현재 로그 공통 필드에는 customerId도 없으므로 고객 ID만으로 실패 로그가 항상 찾아진다고 가정하지 않는다.

## 4. 김아름의 구현에 미칠 영향

| 항목 | Agent가 지킬 조건 | VOC에서 필요한 동작·우회 |
| --- | --- | --- |
| 재전송 | 같은 키는 기존 실행만 반환; 모델 재호출 없음 | 새로고침·polling·전달 재시도에 새 키를 생성하지 않음 |
| 비용·인증 실패 | 사용자 정보 부족과 구분, 구조화된 오류 | 비용 제한을 추가 입력 폼으로 보내지 않음. 영구 오류는 자동 반복 안 함 |
| 새 오류 코드 | 기존 상태/ApiError 형식 유지 | 모르는 code도 message·retryable로 표시하는 기본 오류 화면 |
| 상태 조회 | GET은 저장 상태만 읽고 모델을 호출하지 않음 | 마지막 결과·lastSyncedAt·syncError 보존, 종료 상태에서 자동 polling 종료 |
| 대기열 | QUEUED를 영속 저장하고 처리 동시성·대기 한도를 명시 | 모델 실행 제한 시간과 접수 후 전체 대기 시간을 구분. polling 종료를 실제 조사 실패로 표시하지 않음 |
| 근거 크기 | 요약 API에 대용량 원문을 반복 포함하지 않음 | 클릭 시 evidence GET으로 원문 로드. 로그·코드는 실행되지 않는 텍스트로 표시 |
| NEEDS_INPUT | 허용 context 필드와 reason 반환 | 티켓 수정으로 버전 증가 후 새 키·previousInvestigationId로 재조사 |
| 모델 변경 | 같은 조사 안의 내부 모델 전환은 같은 investigationId 유지 | 분석 이력이 모델 전환 횟수만큼 중복 생성되지 않음 |
| 기술 사용량 | 기본은 Agent 내부 메타데이터; 공용 DTO 확장 시 optional | 기존 리포트·화면을 깨뜨리지 않고 관리자용 표시 여부 별도 결정 |
| 시연 환경 | LLM 키는 Agent에만, 서비스 인증은 별도 | 웹 서버/Agent 환경 변수 이름·주소 일치. 브라우저에 LLM 키 없음 |
| 평가 실행 | 입력·근거·모델 호출 기록을 실제로 남김 | runner가 상태 200/COMPLETED만 보고 PASSED를 쓰지 않음 |

새 오류 **제안**: `LLM_CONFIGURATION_ERROR`, `LLM_UNAVAILABLE`, `INVESTIGATION_BUDGET_EXCEEDED`.
현재 v1에 없는 코드다. 추가 시 [연동 계약](../integration-contract.md), VOC의 fallback 표시, 재시도 규칙을 같이 검토한다.
예산 부족은 기본 retryable=false로 제안한다. 같은 키 재전송은 비용을 다시 쓰지 않으며,
한도·설정 해결 후 사용자가 의도한 새 조사만 새 키로 시작한다. 이 문서 작성만으로 계약을 변경한 것은 아니다.

## 5. DONE 절차에서 확인한 실제 영향

[scripts/jdd.py](../../scripts/jdd.py)의 `completion_fingerprint`, `role_done`, `verify_mvp`, `publish`를 읽고 확인했다.

1. `docs/status/` 밖의 추적 파일은 경로·모드·내용까지 완료 fingerprint에 포함된다. 프롬프트·계획 문서 수정도 DONE을 STALE로 만든다.
2. status만 바뀌면 완료 fingerprint는 유지되지만 buildId에는 커밋 SHA가 들어간다. 같은 내용이라도 후속 기동의 buildId는 달라질 수 있다.
3. publish는 전체 check→재기동→smoke다. live LLM 시나리오는 직접 실행하지 않는다. role-done은 verify-mvp를 실행한다.
4. role-done은 세 앱의 businessReady와 전체 시나리오를 요구한다. Agent 단독 완료를 DONE으로 올릴 수 없다.
5. verify_mvp 결과 검증은 필수 case ID·PASSED·mocked=false·model·buildId를 확인한다. 상세 행동의 정확성은 scenario-runner 테스트가 책임진다.
6. DONE의 검증 요약에는 case별 근거 식별자나 토큰·설정 원문이 보존되지 않는다. 상세 보고서를 로컬 산출물로 별도 보관해야 한다.
7. .env와 외부 API의 실제 모델/설정은 Git fingerprint에 포함되지 않는다. 같은 코드 해시만으로 세 PC의 실행 조건이 같다고 판단할 수 없다.
8. 현재 중단한 미커밋 구현 초안이 남아 있어 clean-main 조건을 통과할 수 없다. 이를 문서 작업을 위해 강제 삭제하거나 검증 없이 커밋하면 안 된다.
9. 원격 `34cdca3`의 품질 기준은 각 VOC 초기화 후 3회, VOC-07은 총 20회의 안정된 재현을 요구한다. 이 기준은 커머스 재현 횟수이며 매회 LLM 호출을 요구하지 않는다. 현행 scripts의 요약 검증만으로 반복 재현 횟수·알려진 오류 부재까지 보장되지 않는다.
10. `e6280e5`부터 roles-check는 세 DONE을 확인하는 중간 단계다. team-check에는 리더 APPROVED가 추가로 필요하며 lead-approve는 새 verify-mvp를 수행한다. 검토 기록의 필수 항목·횟수 검증이 실제 코드 검토와 실행을 대신하지 않는다.
11. lead.json의 승인은 코드 내용뿐 아니라 lead-review.json과 세 역할 완료 기록에도 연결된다. 일반 status-only 변경과 달리 검토 기록·담당자 완료 기록 변경은 리더 승인을 무효화할 수 있다.

### 비용·재검증 반복을 줄이는 절차

- 담당 기능이 준비되면 Markdown에 `기능 준비됨 / 전체 통합 대기`로 사실을 기록한다. JSON DONE은 실제 전체 통과 뒤에만 기록한다.
- 코드·계약·프롬프트·평가 기준을 먼저 공유하고 마지막 검증 구간에는 필수 수정 외 변경을 모아 조율한다.
- 같은 고정 내용에 대해 승인된 데모 범위에서 각 PC의 실제 role-done과 리더 검증을 계획한다. 실행 조건이 없으면 외부 입력 대기로 기록하며 다른 PC 결과를 자기 검증으로 복사하지 않는다.
- 평가 모델·프롬프트 해시·비밀을 제외한 실행 옵션·데이터 실행 식별자를 보고서에 남긴다. 계정별 키 값은 기록하지 않는다.
- `verificationProfileId` 같은 선택적 평가 설정 지문을 runner 보고서에 추가하는 방안을 김아름과 검토한다. 공통 판정에 강제하려면 scripts·세 JSON 스키마·테스트도 변경해야 하므로 별도 작업이다.
- 자기 완료 후 변경·요청이 없으면 약 60초 원격 확인만 수행한다. 상태 확인과 polling은 LLM을 호출하지 않는다.
- 실패 발견 시 `role-reopen agent`, 변경 반영 후 실제 재검증. 타인의 JSON은 수정하지 않는다.
- 개발리더의 lead.md·lead-review.json을 확인하고 Agent 지적을 처리한다. 리더 수정 후 최신 코드에서 자기 DONE을 갱신하며 리더 승인 기록을 대신 작성하지 않는다.
- 최종 goal 종료에는 세 유효 DONE·리더 APPROVED, 깨끗한 최신 main의 `team-check=0`, 실제 필수 품질 기준 충족이 모두 필요하다. 검사 결과가 0이어도 알려진 미해결 문제·검증 누락이 있으면 자기 DONE을 철회한다. 이번 문서 분석은 goal을 시작하거나 완료하는 작업이 아니다.

최소 필수 case는 11종이다. 세 역할 1회씩과 리더의 별도 최종 검증을 합치면 case 실행은 최소 44회다.
각 case의 조사 수·정상 대조 수·재조사·모델 요청 수는 다를 수 있어 **44회 모델 호출**로 계산하면 안 된다.
별도로 커머스 반복 재현 검증 한 묶음은 최소 38회(6종×3회 + VOC-07 총 20회)다. 리더도 자기 실제 재현 기록을 남긴다.
각 실행의 초기화·업무 응답·DB/로그 관측을 보존한다. 이 반복을 매번 유료 조사로 연결하지 않는다.
실제 모델 검증은 승인된 사용 범위·예산 안에서 관련 변경과 최종 통합에 수행한다. 재현 성공과 AI 판단 성공은 별도 지표다.
