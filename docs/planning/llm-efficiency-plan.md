# VOC 조사 LLM의 토큰·비용·효율 계획

확인일: 2026-09-21. API 호출이나 모델 성능 평가는 실행하지 않았다.
데모 제공자는 OpenAI이며 GS 해커톤 프로모션 크레딧을 사용한다. 사용자 제공 계정 화면의 $50.00 적용 금액·2026-09-21 적용일을 기록한 상태이며, 이 세션이 계정을 직접 확인하지는 않았다. 프로모션 코드와 API 인증 키는 별개다.
크레딧 적용 조직·프로젝트와 기존 키의 연결, 모델명·API 주소·실제 접근은 미확정/미검증이다.
가격은 확인한 공식 자료의 비교 예시다. $30 초과 예상 시 별도 처리한다는 기준은 확정됐고, 예산 기간·공유 범위·조사당 한도는 미정이다.
기본 목표는 **인용·원인 판단·정상 대조 기준을 만족하는 조사 한 건의 총비용과 지연을 최소화하는 것**이다.

이 문서의 실험·평가 제안에는 [데모 키·비용·로컬 실행 규칙](demo-llm-policy.md)을 우선 적용한다.
개발·일반 테스트·CI·자동 반복 평가에서는 제공된 키를 사용하지 않는다. 모의 모델과 합성 usage로 구현·계측을 검증한다.
실제 모델 비교는 승인된 데모 범위와 예산 안에서만 수행한다. 유료 개발 실험이 필요하면 모델·호출 수·최악 비용과 별도 사용 범위를 먼저 정한다.
키가 있거나 예상액이 $30 미만이라는 이유로 API를 호출하지 않는다. 아래 가격 비교와 한도 제안은 유료 실행 허가가 아니다.
확인된 적용 금액은 현재 잔액이 아니며 적용일은 만료일이 아니다. 실제 잔액·만료일·모델 제한이나 API 키의 적용 여부는 미확인이다.
크레딧은 사용량 0이나 예산 확대를 뜻하지 않는다. 아래 사용량 기반 비용과 실제 크레딧 차감·청구를 구분한다.
크레딧이 소진·만료됐을 때 별도 결제로 자동 계속하도록 설정하지 않으며 데모 전용·$30 기준은 유지한다.

## 1. 모델 선택 방법

특정 모델을 가장 효율적이라고 미리 확정하지 않는다. 현재 OpenAI의 세 후보를 비용 민감형·균형형·상위형 비교군으로 사용할 수 있다.
모두 문서상 function calling과 structured outputs를 지원하지만 실제 계정 접근·Spring AI 연동·한국어 VOC 품질은 별도 검증해야 한다.
[Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna), [Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra), [Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol).

아래 단가는 Standard·short context·텍스트 100만 토큰당 USD다. 캐시 쓰기는 일반 입력과 별도 가격 구분이다.

| 비교 후보 | 일반 입력 | 캐시 읽기 | 캐시 쓰기 | 출력 |
| --- | ---: | ---: | ---: | ---: |
| gpt-5.6-luna | 0.20 | 0.02 | 0.25 | 1.20 |
| gpt-5.6-terra | 2.00 | 0.20 | 2.50 | 12.00 |
| gpt-5.6-sol | 4.00 | 0.40 | 5.00 | 20.00 |

출처: [공식 API 가격](https://developers.openai.com/api/docs/pricing).
Fast·Batch·지역 처리·장문 가격과 혼용하지 않는다. Sol의 현행 요금은 프로모션 표기이므로 적용 시점에 재확인한다.
세 후보의 문서상 272K 초과 입력은 해당 요청 전체의 입력·출력 단가에 영향을 준다.
큰 context window는 보내야 할 목표량이 아니다. 이 프로젝트는 먼저 작은 근거 묶음으로 처리한다.

선정 순서(실제 호출은 위 데모 정책의 실행 조건을 갖춘 뒤 수행):

1. 같은 정책·합성 사건·근거 묶음으로 후보별 도구 호출·구조화 출력·판단 품질의 소규모 비교를 수행한다.
2. 실제 재현과 동일 조사 흐름에서 VOC-01~07·정상·정보 부족을 검증한다. 문구·식별자 변경 사례도 포함한다.
3. 필요한 품질을 통과한 모델 중 성공 조사당 비용·지연이 낮은 모델을 기본으로 선택한다.
4. 하위 모델이 실패한 **추론** 사례만 상위 모델로 전환했을 때의 총비용과 정확도를 별도 비교한다.

Luna를 저비용 후보로 시험하고 Terra를 비교 기준으로 둘 수 있다. Luna가 정확도를 충족하지 않으면 기본 모델로 채택하지 않는다.
Sol 전환도 자동 정답으로 간주하지 않는다. 데이터가 없거나 API 인증·도구가 실패한 경우에는 모델을 키우지 않는다.
이 모델 배치는 가격과 공식 모델 설명에 근거한 평가 제안이며 JDD에서 측정한 추천 결과가 아니다.

## 2. 토큰과 비용 집계

한 조사는 여러 모델 호출을 포함한다. 시스템 지시·도구 스키마·이전 대화·새 근거·보고서 수정 요청이 각 호출의 입력에 들어갈 수 있다.
최종 응답 한 번의 토큰만 조사 비용으로 기록하지 않는다.
한국어 글자 수나 영어의 대략적인 글자/토큰 비율로 모든 모델을 동일 계산하지 않는다.
개발에서는 모델별 로컬 tokenizer와 합성 payload로 추정한다. 외부 토큰 계산 API도 키를 자동 사용하지 않으며 승인된 실행 범위에서만 호출한다.
실제 데모에서는 지원되는 입력 토큰 계산과 응답 usage로 추정값을 보정한다.
[공식 토큰 계산 문서](https://developers.openai.com/api/docs/guides/token-counting).

OpenAI의 위 후보에 적용할 개별 호출 비용식:

```text
I = 응답 usage의 전체 입력 토큰
R = 입력 토큰 중 캐시 읽기 토큰
W = 입력 토큰 중 캐시 쓰기 토큰
U = I - R - W
O = 전체 청구 출력 토큰

호출 비용 = (U × 일반 입력 단가
           + R × 캐시 읽기 단가
           + W × 캐시 쓰기 단가
           + O × 출력 단가) / 1,000,000
조사 비용 = 해당 조사의 모든 실제 모델 호출 비용 합계
```

단가는 모델·API 경로·service tier·입력 길이 구간·가격 적용일로 선택한다.
R/W를 제공하지 않는 연동에서 null을 관측된 0으로 바꾸지 말고 `UNKNOWN`으로 표시한다.
입력/캐시 집계 의미가 다른 제공자는 해당 native usage를 이 장부의 서로 겹치지 않는 범주로 변환한다.
정규화 검증에 실패하면 비용 확정값을 만들지 않는다.

Reasoning 토큰은 표시된 답변보다 많을 수 있고 출력 청구에 포함된다. 이미 O에 포함된 reasoning을 다시 더하지 않는다.
출력 제한은 최종 한국어 보고서뿐 아니라 모델이 생성하는 다른 토큰도 고려한다.
[Reasoning 비용·출력 한도](https://developers.openai.com/api/docs/guides/reasoning).

### 계산 예시 — 실측값 아님

조사 전체 호출의 합계가 일반 입력 20,000, 출력 4,000토큰이며 캐시 읽기·쓰기가 모두 0인 경우를 가정한다.
출력 4,000에는 reasoning이 있으면 그 사용량도 포함한다. 세금·외부 도구 비용은 제외한다.

| 모델 | 조사당 가정 비용 | 동일한 조사 44건의 가정 비용 |
| --- | ---: | ---: |
| Luna | $0.0088 | $0.3872 |
| Terra | $0.0880 | $3.8720 |
| Sol | $0.1600 | $7.0400 |

이는 같은 토큰 수를 대입한 산술 비교다. 실제 모델별 입력·출력·reasoning·재시도 수는 다르다.
44는 11개 필수 case×(세 역할 검증 + 이상효의 별도 리더 최종 검증)이라는 비교용 숫자다. 리더는 별도 네 번째 PC가 아니다.
실제 case당 조사 수와 모델 호출 수, 실패·수정 후 재검증은 별도 집계한다. 이 산술 예시는 $30 이내 완료 보장이나 실행 승인이 아니다.

Luna 실행 후 20%를 같은 가정 비용의 Terra로 추가 처리하면 평균은 `$0.0088 + 0.2 × $0.088 = $0.0264`다.
전환 비율·후속 토큰·품질은 측정하지 않았으므로 절감 보장값으로 사용하지 않는다.

## 3. Spring AI 연동에서 필요한 계측

공식 Spring AI 2.0.1 문서상 도구 반복의 `getUsage()`는 누적값이다.
이는 연동 시 확인할 후보 버전의 동작이며 현재 프로젝트에 해당 버전이 설치됐다는 의미는 아니다.
개별 호출 장부와 최종 누적 usage를 둘 다 합산하면 이중 계산이다. 누적값은 개별 합계와 대조하는 용도로 사용한다.
여러 호출을 합산한 응답의 native usage는 null일 수 있으며, 문서의 OpenAI 표에는 캐시 쓰기 매핑도 지원되지 않는 것으로 표시된다.
따라서 개별 provider 응답 경계에서 native/raw usage의 필요한 수치만 수집하고,
새 OpenAI 캐시 쓰기 필드를 현재 Spring AI/SDK가 보존하는지 계약 테스트로 확인한다.
[Spring AI 사용량 문서](https://docs.spring.io/spring-ai/reference/api/usage-handling.html).

Spring AI의 OpenAI Chat 연동과 OpenAI Responses는 동일한 요청 형식이 아니다.
cache breakpoint·token counting·reasoning 옵션을 Chat Completions 요청에 그대로 넣지 않는다.
필요 기능이 현행 클라이언트에 없다면 LLM port 뒤의 좁은 Responses adapter 또는 지원 가능한 연동 경로를 검토하고,
단순 접속 성공이 아닌 tool calling·structured output·사용량 보존으로 호환성을 검증한다.
[Spring AI OpenAI Chat](https://docs.spring.io/spring-ai/reference/api/chat/openai-chat.html).

도구 반복에는 하나의 소유자만 둔다. Spring AI 2.0의 ToolCallingAdvisor를 사용하면서 별도 반복기를 중복 실행하지 않는다.
수동 반복을 택하면 자동 반복과 충돌하지 않는 구성을 확인하고, 각 iteration의 예산·상태·사용량을 직접 관리한다.
[ToolCallingAdvisor](https://docs.spring.io/spring-ai/reference/api/tools/tool-calling-advisor.html).

장부에 필요한 최소 정보:

| 구분 | 기록 |
| --- | --- |
| 연결 | investigationId, 내부 modelCallId, provider request ID, attempt 번호 |
| 모델 | 요청 모델·실제 응답 모델, endpoint, service tier, 비밀 제외 모델 옵션 |
| 입력 | prompt 버전·해시, 도구 스키마 버전, 요청의 예상 토큰 |
| 실제 사용 | input/output, cache read/write, reasoning, 값의 출처와 UNKNOWN 여부 |
| 비용 | 단가 버전·적용일, 예상·관측 비용, 보류 중인 예약 금액 |
| 운영 | 시작·종료·지연, 성공·실패·취소·응답 유실, 전환 사유 |

각 실제 HTTP 시도는 새 attempt로 기록하되 같은 응답 이벤트를 중복 수신하면 비용 장부에 중복 적재하지 않는다.
실패·형식 재시도·모델 전환도 합산한다. timeout으로 usage를 받지 못하면 0원이 아니라 미확정 비용으로 남긴다.
raw reasoning 내용은 저장·출력 대상이 아니며 필요한 것은 사용량 수치다.

## 4. 토큰을 줄이는 우선순위

1. **중복 실행 제거:** 요청 키로 조사 하나를 만들고 하나의 worker만 claim한다. 재전송·polling·근거 열람은 LLM 호출 0회다.
2. **서버의 결정적 처리:** 식별자 검증, 시간 정규화, 산술 집계, 근거 ID 발급, JSON·참조 검증을 Java/SQL에서 수행한다.
3. **대상을 좁힌 조회:** 요청·주문·상품·시간으로 필터링하고 관련 컬럼·로그 구간·소스 줄만 가져온다.
4. **원문과 모델 입력 분리:** 원문은 근거 저장소에 보존한다. 모델에는 결정적 필드·관련 문맥·근거 ID를 주고 필요할 때 확대 조회한다.
5. **반복 대화 절제:** 이미 읽은 대형 원문을 매번 다시 추가하지 않는다. 도구 호출/결과 연결을 보존하며 불필요한 이전 내용을 줄인다.
6. **안정된 프롬프트 앞부분:** 시스템 규칙·고정 도구 스키마를 앞에 두고 문의·시각·동적 근거는 뒤에 둔다.
7. **최소 추가 호출:** 형식 오류 수정에는 관련 오류·필요한 근거만 제공하고 전체 조사를 반복하지 않는다.
8. **측정 후 모델 조정:** 기본 모델·reasoning 설정을 평가로 고르고 관측 가능한 실패 조건에서만 제한적으로 전환한다.

후보 도구가 8개인 현재 범위에서는 먼저 짧고 안정된 도구 스키마를 사용한다.
동적 도구 분류를 위한 별도 LLM 호출은 그 호출·캐시 손실까지 포함해 이득이 확인될 때만 추가한다.
추가 LLM 요약기도 기본으로 넣지 않는다. 결정적 필드 선택으로 충분한지 먼저 확인한다.
사실을 지우는 축약·단순 문자열 잘라내기는 금지하고, 더 볼 필요가 있으면 원문 조회로 되돌아갈 수 있어야 한다.

### 캐시의 두 종류

- **불변 자료 캐시:** 소스는 buildId+파일 해시+줄 범위, 정책은 버전+내용 해시로 재사용한다. 새 조사에서 인용하면 그 조사 소속의 근거를 저장한다.
- **동적 조회:** DB·로그는 조사/실행 범위·필터·관측 시점을 포함한다. 초기화·새 요청·데이터 변경 후 전역 재사용하지 않는다.

모델 prompt cache는 위 자료 캐시와 다르다. GPT-5.6 이후에는 읽기 할인뿐 아니라 쓰기 비용이 있고, 최소 cacheable prefix와 breakpoint 정책이 있다.
고정 prefix 재사용 횟수·cache_read/cache_write를 측정하고 동적 suffix를 불필요하게 cache-write하지 않는 구성을 검토한다.
캐시를 켰다는 이유로 모든 입력에 할인 단가를 적용하지 않는다. 과금할 토큰을 억지로 추가해 prefix를 늘리는 최적화는 기본안으로 사용하지 않는다.
[OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching).

## 5. 예산·시간·호출 제한

**아래 숫자는 초기 실험 제안이며 사용자 예산·완료 기준으로 확정된 값이 아니다.**

| 설정 | 실험 시작안 | 목적 |
| --- | --- | --- |
| 전체 모델 요청 | 조사당 최대 6회 | 보고서 생성·수정·상위 모델 전환까지 같은 상한에 포함 |
| 전체 도구 실행 | 조사당 최대 20회 | 새로운 관측 없이 같은 검색 반복 방지 |
| 모델 입력 | 호출당 12K 목표, 조사 누적 40K 상한 | 단일 context와 누적 청구량을 별도 관리 |
| 모델 출력 | 호출별 2K~4K에서 시험, 조사 누적 8K 상한 | reasoning+보고서의 실제 소모를 보고 조정 |
| 시간 | 조사 180초, 모델 요청 60초 이내에서 시험 | 남은 전체 deadline을 각 요청에 전달 |
| 동시 모델 호출 | PC당 1부터 시작 | DB·provider rate limit과 실제 지연에 맞춰 확대 |
| 금액 | 데모 누적 $30 초과 예상 시 새 호출 차단·별도 처리 | 기간·공유 범위·조사당 배분은 확정 후 설정. 개발 허용액으로 해석하지 않음 |

이 상한들은 동시에 모두 소비 가능한 할당이 아니다. 다음 요청의 예상 입력과 출력 예약량이 남은 토큰·금액·시간에 들어갈 때만 전송한다.
출력 제한을 너무 낮게 설정하면 보고서가 잘리거나 reasoning만으로 소진될 수 있다. 미완성 응답을 파싱 성공으로 간주하지 않는다.
종료 보고서에 필요한 호출·출력 예산을 조사 초기에 남겨 두고, 이를 소진하는 추가 검색은 멈춘다.
이 실험안의 조사 시간은 worker가 RUNNING으로 선점한 뒤의 실행 예산이다. QUEUED 최대 대기·대기열 수용량은 별도로 설정한다.
접수 후 총 대기 시간을 VOC polling 정책과 맞추고, 대기열 과부하의 접수 응답·재시도 규칙을 김아름과 합의한다.
화면의 조회 한도가 끝났다고 Agent의 실제 실행 상태를 바꾸지 않는다.

금액 예산은 응답 후 합계 검사만으로 관리하지 않는다. 호출 전 보수적 비용 예약→실제 usage 정산을 수행한다.
기본 실행 경로는 유료 호출 금지다. 명시한 데모 모드·유료 호출 허용·모델 가격·예산이 모두 준비된 경우에만 호출한다.
확정 비용 + 미확정 비용 + 진행 중인 예약 + 새 요청의 최대 예상 비용을 합산해 허용 여부를 원자적으로 판단한다.
예약·정산은 영속 저장하며 재시작·새 requestKey·재조사·모델 전환이 누적 한도를 초기화하지 않도록 한다.
가격이나 사용량을 확인할 수 없거나 합계가 $30을 넘길 것으로 예상되면 새 유료 호출을 시작하지 않고 별도 처리 사유를 기록한다.
캐시 적중을 확신할 수 없으면 할인 없는 경우와 가능한 write 비용을 반영한다.
전송 후 timeout·취소된 요청은 제공자에서 이미 처리됐을 수 있으므로 미확정 예약량을 무조건 환급하지 않는다.
클라이언트 한도는 추가 요청을 통제하는 장치이며 제공자 청구를 원자적으로 취소하는 보장은 아니다.

429 중 일시 rate limit과 잔액·할당량 부족을 구분한다. 유효한 Retry-After를 존중하고 없으면 jitter가 있는 backoff를 사용한다.
SDK와 애플리케이션의 재시도 횟수를 중첩하지 않는다. 재시도는 전체 deadline·요청 수·비용에 포함한다.
RPM·TPM·프로젝트/조직 한도를 확인하고 세 PC가 같은 계정 한도를 공유하면 평가 시간을 나누거나 총한도를 분배한다.
각 PC의 로컬 카운터 하나로 조직 전체 예산이 보장된다고 가정하지 않는다.
공유 예산은 공용 장부 또는 총합이 허용액 안에 드는 PC별 배분으로 관리한다. 세 PC에 각각 $30을 부여하지 않는다.
[OpenAI rate limits](https://developers.openai.com/api/docs/guides/rate-limits).

## 6. 모델 전환과 종료 상태

- 같은 조사에서 근거는 확보됐지만 복잡한 인과관계·정상 대조 판단을 충족하지 못할 때만 상위 모델 전환을 검토한다.
- 모델의 자가 확신 점수나 시나리오 ID만을 전환 조건으로 삼지 않는다. 검증 실패·반대 근거 처리·평가에서 확인된 조건을 사용한다.
- 전환은 한 번부터 시험하고 동일 조사 예산에 포함한다. 기존 관측은 보존하되 다른 모델의 내부 reasoning 상태를 그대로 넘기지 않는다.
- 실행마다 실제 사용 모델을 모두 기록한다. 최종 모델만 기록하고 이전 호출 비용을 누락하지 않는다.
- 정보 부족은 NEEDS_INPUT, 도구·설정·비용 한도로 필수 조사를 수행하지 못하면 FAILED다. 비용 절감을 이유로 가짜 COMPLETED를 만들지 않는다.
- 비용 오류 코드와 retryable 규칙은 김아름의 화면·재시도 계약과 함께 확정한다.

## 7. 평가·DONE 비용 관리

개발 중에는 모의 모델로 계약·수치·참조·복구와 비용 예약을 검증하고 실제 API 호출이 0회인지 확인한다.
제공된 데모 키로 개발·CI·자동 반복 평가를 실행하지 않는다. live 검증은 승인된 데모 실행 계획에 모델·호출량·최악 비용을 포함한 뒤 수행한다.
up/check/publish/verify-mvp/role-done/lead-approve라는 명령 자체를 유료 호출 허가로 취급하지 않는다.
실제 모델 검증을 수행하지 못하면 미검증으로 남기고 DONE·리더 승인을 작성하지 않는다.
같은 저장된 관측으로 여러 모델의 보고서를 비교하는 실험은 유용하지만 실제 도구 조회를 포함한 최종 MVP 검증을 대체하지 않는다.
Batch 할인은 대기 가능한 독립 오프라인 비교에 한해 검토하고 즉시 결과를 기다리는 VOC 조사 경로에 바로 적용하지 않는다.

측정할 지표:

- 성공 조사당 비용 = 실패·재시도·전환을 포함한 전체 비용 / 기준을 만족한 조사 수. 분모 0이면 산출 불가.
- 인용 유효성·정상 오진·원인 판단·형식 실패와 재조사율.
- 조사당 모델/도구 호출 수, input/output/reasoning/cache read/write, 미확정 비용.
- 지연 중앙값·최댓값. 작은 표본의 p95는 충분한 표본을 모으기 전 일반화하지 않는다.
- 모델·prompt/도구 스키마 버전·runtime 설정·데이터 실행 범위.

[DISC-20260921-voc-001 P1](../discussions/DISC-20260921-voc-001-runner-metadata.md)에 세 담당자가 합의했다.
runner의 기존 필수 계약을 유지하고 `modelsUsed`, `usageSummary`, `verificationProfileId`의 생성·필수 판정 추가는 보류한다.
한재홍이 실제 관측 DTO·조회 경로·단위·누락 표현을 후속 제안으로 제공하면 김아름이 소비·표시를 검토하고 이상효가 검증 영향을 확인한다.
그 합의 전에는 알 수 없는 사용량을 0이나 설정값으로 채우거나 추가 관측만을 위한 유료 호출을 하지 않는다.
기존 `model`은 실제 최종 응답에서 확인한 모델을 기록한다. 선택 필드의 구현은 이번 범위 결정 논의의 해소 조건이 아니며,
실제 모델 검증·비용 보호·기존 완료 판정은 그대로 유지한다.
역할 완료는 고정한 코드·계약·프롬프트에 대해 각 PC에서 실제 role-done으로 검증한다.
세 DONE 이후 이상효의 독립 코드 검토·지적 해결·새 verify-mvp와 리더 APPROVED가 추가로 필요하다.
리더의 모델 호출도 같은 사용 제한과 누적 비용 계획에 포함한다. 다른 담당자의 성공 보고서로 새 검증을 대체하지 않는다.
리더가 코드를 수정하면 담당자 재검증과 리더 재검증 비용이 다시 발생할 수 있으므로 최종 검증 전에 수정·정책을 모아 확정한다.
60초마다 수행하는 원격 완료 확인은 유료 모델 검증을 다시 실행하지 않는다.
원격 `34cdca3`에서 추가된 각 VOC 3회·VOC-07 총 20회 기준은 커머스 재현 반복이다.
한 번의 반복 재현 검증 묶음인 최소 38회에 매번 LLM을 붙이지 않는다. 리더의 반복 재현 기록도 실제 실행으로 남긴다.
관련 변경·최종 통합의 실제 모델 검증은 사용 범위와 예산 안에서 별도 계획한다.

구체적인 연동 위험과 인계는 [Agent 통합 영향 분석](agent-integration-risk-review.md)에 정리했다.

## 8. 구현 전에 확정할 외부 입력

- OpenAI API endpoint·접근 가능한 모델·데모 환경의 비밀 주입 경로. 프로모션 적용 조직·프로젝트와 기존 API 키의 연결은 확인이 필요하며 재발급을 선행 조건으로 추가하지 않는다.
- 프로모션의 실제 잔액·만료일·모델 제한. 사용자 제공 적용 금액 $50.00·적용일 2026-09-21과 구분하며 프로모션 코드를 API 인증 값으로 전달하지 않는다.
- $30 기준의 예산 기간·팀 공유 범위와 조사당/일일 배분. 위 실험 토큰 한도는 개발 지출 승인 금액이 아니다.
- 평가에 쓸 모델 버전·옵션과 상위 모델 전환 허용 여부.
- 세 PC가 같은 provider 프로젝트를 공유하는지, 평가 시간을 나눌지와 시연 PC의 ngrok 접속 주소.
- 데모 방식은 [로컬 앱 + ngrok](../ngrok-local-demo.md)다. OpenAI 호출은 로컬 Agent가 직접 수행하며 사용량·프로모션·$30 기준은 유지한다. ngrok 계정·접근 제어·공개 URL의 실제 연결은 준비·검증이 필요하다. 로컬 LLM 전환은 이번 선택에 포함되지 않는다.

미정 값은 설정·구현 인터페이스와 구분해 남겨 두며 API 키를 문서·프롬프트·Git에 기록하지 않는다.
