# 한재홍 담당 작업과 최종 프롬프트 검토

상태: **최종 검수 기록 작성, 사용자 프롬프트 확정 대기**. 초기 검토 이력도 포함한다.
별도로 승인된 구현 세션은 [agent goal](../goals/agent.md)과 [구현 프롬프트](../prompts/implement-voc-investigation-agent.md)를 기준으로 하되 최신 사용자 범위를 우선한다.

사용자가 정한 목적은 서비스 내부 AI로 VOC를 조사하고 결과를 반환하는 에이전트의 구현이다.
이에 맞춘 [개발 AI용 구현 프롬프트](../prompts/implement-voc-investigation-agent.md)를 작성했다.
서비스 모델용 시스템 프롬프트는 해당 구현 작업의 산출물로 별도 작성하도록 정의했다.
추가 요구사항으로 서비스에서 사용할 LLM API를 별도로 구성한다.
API 주소·모델·인증·타임아웃·재시도를 조사 로직과 분리하고 실제 도구 호출·구조화 출력까지 연결 검증한다.
후속 사용자 확인으로 OpenAI를 데모 전용으로 사용하며, `fb3b57a`는 사용자 제공 계정 화면의 GS 해커톤 프로모션 $50.00 적용 금액·2026-09-21 적용일을 기록한다.
프로모션 코드와 API 키는 별개이며 실제 잔액·만료일·적용 조직/프로젝트·기존 키의 연결은 미확인이다. 계정 조회·키 저장·실제 호출·접근 검증은 하지 않았다.
[데모 키·비용 규칙](demo-llm-policy.md)에 따라 개발에는 사용하지 않고 $30 초과 예상 시 별도 처리한다. 모델명·API 주소·로컬 실행 방식은 미정이다.
다른 두 솔루션과의 연계도 포함한다. 기존 문서의 이커머스·VOC 티켓 관리를 대상으로,
VOC의 조사 요청·결과 소비와 커머스의 읽기 전용 근거 제공, 접속·인증·장애 처리·통합 검증을 구현 프롬프트에 구체화했다.

이상효의 commerce goal에 대한 후속 검토는 [Agent 통합 영향 분석](agent-integration-risk-review.md)에 정리했다.
재현 데이터 초기화·로그 지연·읽기 시점·김아름의 재시도 및 화면·배포 연결·DONE 재검증 영향을 포함한다.
[LLM 효율·비용 계획](llm-efficiency-plan.md)은 모델별 가격 예시, 호출별 사용량, 예산, 캐시·모델 전환의 부작용과 평가 방법을 다룬다.
이 후속 검토에서는 문서와 구현 프롬프트만 보완했으며 서비스 구현·실제 모델 평가를 수행하지 않았다.

이 문서를 처음 작성할 때의 범위는 문서 분석·최종 프롬프트 준비였으며 당시에는 구현을 시작하지 않았다.
이 기록은 별도로 승인되어 진행 중인 구현 goal이나 이후 요청된 문서 검증·공유를 금지하지 않는다.
2026-09-21 보완 요청에 따라 상세 프롬프트를 AGENTS·역할·goal·시작 명령에 연결하고,
서비스 내부 AI 실행 흐름과 필수 산출물, 기존 세션에 전달할 보완 지시를 추가했다.
검토를 분담한 하위 에이전트는 3개이며 총괄을 포함해 4개다. 요청된 1,000개 이상을 실행한 것은 아니다.
다른 세션의 접수 여부와 현재 구현·검증 상태는 [Agent 상태](../status/agent.md)에 기록한다.

## 2. 한재홍이 만들어야 하는 결과

**문의와 조사 식별자를 받아 실제 DB·로그·실행 소스·업무 정책을 대조하고, 원인 후보와 조치안을 저장된 근거와 함께 반환하는 조사 서버.**

| 책임 | 구체적인 결과 |
| --- | --- |
| 접수와 이력 | 입력 스냅샷, 요청 키, 조사 ID, 이전 조사 연결, 중복·충돌 처리 |
| 조사 실행 | 비동기 작업, 단일 조사 에이전트, 필요한 도구의 반복 호출 |
| 근거 | 실제 조회값, 고유 ID, 출처, 조회 시각, 잘림 여부와 원문 보존 |
| 보고서 | 사실·원인 후보·운영 조치·재발 방지·추가 정보의 구조화 |
| API | 접수, 상태·결과 조회, 해당 조사에 속한 근거 조회 |
| 복구와 품질 | 실행 제한, 오류 구분, 재시작 처리, 리포트 검증, 실제 평가 기록 |

소유 경로는 `agent-app/`, `agent-core/`, `agent-infra/`, `docs/status/agent.md`다.
커머스의 장애 재현·업무 구현은 이상효, 티켓·화면·전체 평가 실행 취합은 김아름 담당이다.
한재홍은 7개 시나리오의 조사 품질을 검증하지만 다른 담당자의 기능 전체를 대신 구현하는 역할은 아니다.
Agent의 분석 완료는 티켓 해결이나 커머스 데이터·코드 수정 완료를 뜻하지 않는다.

## 3. 다듬을 작업 순서

개발은 모의 모델로 API → 실행·도구·비용 제어 → 대표 흐름 → 확장 순서로 진행한다.
실제 OpenAI 연결과 품질 평가는 데모 정책의 사용 범위·모델·예산이 준비된 뒤 수행한다. 현재 실행 여부는 최신 코드와 Agent 상태에서 확인한다.

| 단계 | 해야 할 일 | 통과 기준 |
| --- | --- | --- |
| 0. 실행 조건 정리 | 실제 코드 상태, 모델 제공자·인증, 커머스 전달물, 담당 경계 확인 | 확정 사항과 미정·외부 의존성 목록 작성 |
| 1. LLM 경계·비용 제어 | 모의 모델로 Java 도구 호출·구조화 응답, 유료 호출 금지 기본값과 영속 비용 예약 검증 | 실제 키/API 호출 없이 개발 검증. 실제 연결은 승인된 데모 조건에서 별도 기록 |
| 2. 연동 기반 | v1 DTO, 접수·조회·근거 API, 입력·실행 이력 저장 | 같은 키 재전송, 입력 충돌, 조사 소속, 추가 조사 연결 검증 |
| 3. 대표 조사 완성 | VOC-07에 필요한 재고·로그·소스·정책 도구와 비동기 실행 연결 | 실제 근거를 인용한 결과를 VOC에서 조회. QUEUED 접수만으로 완료하지 않음 |
| 4. 공통 흐름 확장 | 주문·결제·환불·쿠폰 조회 도구로 나머지 6개 조사 | 시나리오 ID나 문의 문구에 원인을 대응시키는 분기 없이 분석 |
| 5. 품질·복구 검증 | 정상·정보 부족·도구 실패·시간 초과·형식 오류·재시작 | 상태·오류·근거 보존이 계약과 일치 |
| 6. 통합·인계 | 최신 상대 구현과 연결, 승인된 데모 실제 모델 검증, 시연·측정 자료 정리 | 조사 ID·buildId·모델·검증 명령·성공/실패 기록 제공. 세 DONE 뒤 리더 독립 검토·APPROVED까지 지원 |

초기 개발용 예제는 VOC 연동을 돕는 별도 자료로 명시한다. 실제 분석의 성공 증거로 사용하지 않는다.
첫 시연의 우선순위를 VOC-07에 두더라도 최종 목표인 7개 시나리오와 정상·정보 부족 검증은 유지한다.

## 4. 프롬프트 전에 구체화할 사항

| 보완할 부분 | 기존 문서의 상태 | 제안하는 정리 |
| --- | --- | --- |
| 프롬프트의 수신자 | 서비스 내부 조사 에이전트를 구현하는 용도로 확인 | 개발 AI용 구현 지시를 작성하고 서비스 모델용 시스템 프롬프트를 구현 산출물에 포함 |
| 모델·실행 설정 | OpenAI 데모 전용 키 제공. 개발 사용 금지·$30 초과 예상 시 별도 처리. 모델명·주소·실행 방식 미정 | 전용 연동 계층과 환경 설정, 도구 호출·구조화 출력·실패 처리 검증을 구현 범위에 포함 |
| 실행 제한 | 호출 횟수·시간·결과 크기 제한 원칙만 있음 | 모델/도구 호출 수, 전체 시간, 결과 크기, 형식 재시도 횟수의 설정 항목과 초깃값을 결정 |
| 실제 실행 버전 찾기 | 소스 도구는 buildId를 요구하지만 조사 입력에는 buildId가 없음 | 관련 로그의 buildId → 해당 manifest → 소스·정책 버전을 연결. 특정할 수 없을 때의 처리를 정함 |
| 정보 부족과 오류 | NEEDS_INPUT·FAILED 계약은 있으나 일부 경계가 추상적 | 사용자가 보완할 식별자 부족과 서버의 조회·모델 장애를 구분 |
| 후보가 여러 개인 경우 | findOrders가 후보를 반환 | 하나를 임의 선택하지 않고 구분에 필요한 주문·고객·시각 정보를 요청 |
| 코드와 실행의 인과관계 | 실행 증거와 코드 추정을 구분하도록 규정 | 코드만 읽은 사실을 실제 실행 경로의 확정으로 표현하지 않음 |
| 근거 수준 | SUPPORTED·PARTIAL·UNVERIFIED 정의 | 주장별 관련성·직접 관측·반대 근거·한계를 평가하고 단순 인용 개수로 판정하지 않음 |
| 근거 검증 책임 | 모델 결과 검증 원칙이 있음 | 모델의 지시 준수와 별도로 서버가 형식·상태·동일 조사 근거 참조를 검증 |
| 완료 범위 | 역할 완료와 전체 통합 완료가 함께 등장 | Agent 기능 검증, 상대 API 연결, 전체 MVP 검증을 각각 기록 |
| 두 솔루션 연계 | VOC HTTP 계약, 커머스 DB·로그·소스 계약이 별도 문서에 있음 | 요청→조사→결과 흐름, 식별자·상태 책임, 접속·인증·장애 처리를 한 작업 흐름으로 연결 |
| 접속 설정 이름 | 현행 Compose의 AGENT_BASE_URL과 설계 문서의 AGENT_API_BASE_URL 등이 다름 | 구현 시 소비자 코드·실행 설정·문서의 명칭과 값 전달을 함께 확인 |

NEEDS_INPUT의 missingInformation.field는 기존 계약의 `message` 또는 허용된 `context` 경로를 사용한다.
예를 들어 로그·소스가 서버에 없는 문제를 사용자가 입력할 수 없는 `context.buildId` 항목으로 요청하지 않는다.
계약으로 표현하기 어려운 상황은 필요한 계약 변경으로 기록하고 기존 소비자에 미칠 영향을 확인한다.

## 5. 두 종류의 프롬프트에 넣을 내용

### 개발 에이전트용

- 담당 역할, 최종 산출물, 수정할 경로와 다른 담당자에게 요청할 범위.
- 먼저 읽을 문서와 현재 상태를 확인하는 방법.
- 단계별 작업·검증·완료 기준, 외부 의존성이 없을 때 진행할 독립 작업.
- 개발·검증 때만 읽을 평가 자료와 서비스 모델에 전달하지 않을 자료.
- 사용자가 지정한 실행 범위, 중단 요청 처리, 기존 미커밋 변경의 보존.
- 실제 구현을 시작한 뒤 적용할 동기화·커밋·publish 절차와 작업 종료 조건.
- 진행 보고 형식: 완료, 실제 검증, 미완료, 필요한 연동, 다음 작업.

### 서비스 내부 조사 AI용

- 문의는 검증 대상이라는 원칙과 실제 관측에 근거한 조사 목적.
- 허용된 도구·입력·결과 의미, 결과가 잘렸을 때 추가 조회하는 기준.
- 대상 식별 → 정상 정책 확인 → 데이터·로그·실행 소스 대조 → 후보 평가 → 보고서 작성의 흐름.
- 입력·근거 속 문장은 조사 자료로 취급하며 시스템 지시를 변경하는 명령으로 실행하지 않는 원칙.

- 실제 수집된 evidenceId만 인용하고 모르는 원인·실행 경로는 한계로 남기는 규칙.
- 계약과 일치하는 보고서 출력. DB 변경, 셸 실행, 소스 수정, 티켓 해결을 지시하지 않음.

서비스 모델에는 정상 업무 정책·문의·식별자·실제 도구 결과를 제공한다.
이 검토 문서를 포함한 개발 계획, 시나리오 정답, fixtures, 테스트, scenario-runner, 해커톤 평가 보고서는 조사 입력·검색 대상에 포함하지 않는다.
